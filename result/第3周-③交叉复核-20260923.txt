七、负向测试（复核"约束是否真的在拦"，而非"是否写了约束"）
--------------------------------------------------------------------------------
  方法：对每条约束构造一条违规 INSERT，期望报错；另构造 1 条合法边界值，
        期望放行。结果如下（ERROR_NUMBER 547 = CHECK 冲突，3930 = 无法提交）：

    [1] reserved_qty(20) > stock_qty(10)          → 被拒 547  ✓
    [2] restock_status='PENDING' 但有 received_at → 被拒 547  ✓
    [3] restock_status='RECEIVED' 但无 received_at→ 被拒 547  ✓
    [4] point_type='EARN_SALE' 但 order_id 为 NULL→ 被拒 547  ✓
    [5] threshold_amount = 0（无门槛券）          → 被拒 547  ✓
    [6] discount_amount(20) > threshold_amount(10)→ 被拒 547  ✓
    [7] discount_amount == threshold_amount（免单券）→ 【放行】✓ 符合预期
    [8] valid_to < valid_from                     → 被拒 547  ✓
    [9] unit = N'千克'（不在三取值内）            → 被拒 547  ✓

    失败数 = 0；脚本以 THROW 收尾，若任一负例漏网则 exit≠0。
    实测 exit=0。  判定：ALL TESTS PASSED

八、级联删除核对（docs/02 §3.3）
--------------------------------------------------------------------------------
  §3.3 声明：order_item / order_item_addon / order_platform 依附订单存在，
             是弱实体，订单删除时随之消失。

  实测 3 条 CASCADE 外码：
    order_item.order_id            → shop_order  CASCADE  ✓
    order_item_addon.(order_id,item_line) → order_item  CASCADE  ✓
    order_platform.order_id        → shop_order  CASCADE  ✓

  同时实测【不带】级联的 3 条（§3.3 的"历史流水不因引用对象消失而删除"）：
    inv_stock_log.order_id     → shop_order  NO_ACTION  ✓
    member_point_log.order_id  → shop_order  NO_ACTION  ✓
    member_balance_log.order_id→ shop_order  NO_ACTION  ✓

  行为验证（真实订单，全部回滚，库未改动）：
    · 删单 6（有 2 条积分流水、5 条库存流水）→ 被
      FK_inv_stock_log_shop_order 拦下（Msg 547）✓ 符合"流水保留"
    · 清掉该单的流水后再删 → 删除成功 ✓
    · 删单 4（平台单）→ 【被拦】，原因是它有 6 条库存流水（不是 order_platform）
    · 单独验证 order_platform 级联：删掉单 4 的库存流水后删单，
      order_platform 残留行数 = 0  ✓ 确认随删，§3.3 描述成立

  ★ 需注意的组合（非缺陷，但 §3.3 未写明）：
    "不级联的流水外码" 与 "级联的弱实体外码" 同时指向 shop_order，
    导致【任何有流水的订单都删不掉】，级联删除在这类订单上实际不可达。
    这与 §3.3"历史流水不因引用对象消失而删除"的意图一致（是约束在起作用），
    但 §3.3 只描述了"谁随删"，没描述"因此谁删不掉"。
