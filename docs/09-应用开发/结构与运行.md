## 2. 分层结构与职责

| 层 | 目录 | 负责 | 不应承担 |
| --- | --- | --- | --- |
| 页面层 | `app/pages/`、`app/templates/` | 接收请求、表单基础校验、渲染页面、返回统一响应 | 不直连数据库、不拼 SQL、不决定数据库权限 |
| 业务层 | `app/services/` | 业务规则、角色可执行范围、事务边界、异常归类 | 不把原始数据库异常返回前端 |
| 数据访问层 | `app/dao/` | 参数化 SQL、连接/游标/事务/释放、结果映射 | 不接收模板逻辑、不拼接用户输入 |
| 数据库层 | SQL Server `MilkTeaShop_v01` | 表、约束、视图、角色与权限 | 不依赖页面隐藏按钮保证安全 |

横切（不属于某一层）：`app/config.py` 统一配置、`app/errors.py` 统一错误码与日志。

## 4. 两条调用链（任务要求能讲清）

```text
查询（GET /products/）：
  浏览器 → main/product 蓝图（role_required 校验）→ services.permissions 判定权限
        → dao.db_cursor()（按角色取连接）→ 参数化 SELECT → SQL Server
        → 结果映射 → 模板渲染 / 统一 JSON → 浏览器

修改（下单，④ 已落地）：
  浏览器提交 → 页面层基础校验 → services 业务规则（库存充足、状态可改、明细合法）
            → dao.db_cursor("app", commit=True) 同一事务写 shop_order + order_item
              + order_item_addon + 库存预占/扣减 + inv_stock_log
            → 提交或回滚 → 统一响应 → 浏览器
```

> **行级隔离的约定（④ 复核 P2-2，2026-10-28；⑤ 复核后修正措辞）**：业务层不读 Flask request，顾客场景的 `member_id`
> 一律由**页面层从 session 取出**后传入（`/orders/mine`、`/orders/<id>`、下单均如此）；`list_orders` / `get_order_detail`
> **不校验**它与会话是否一致，因此**顾客分支绝不允许透传请求参数**。
> 唯一豁免点：`GET /orders/` 的 `member_id` 是**员工筛选条件**（该端点需 `order.read`，顾客本来就 403），页面层已显式写成
> `None if current_role() == "customer" else _text("member_id")`。将来新增 `/api/` 接口时，这条是第一个要检查的点。

### 5.1 `DB_AUTH=trusted` 与 `DB_AUTH=sql` 的实质差别（很容易被忽略）

`connection.build_connection_string()` 在 `trusted` 模式下**无视传入的 role**，一律返回 `Trusted_Connection=yes`：

```python
if Config.DB_AUTH == "trusted":
    return base + "Trusted_Connection=yes;"      # 所有连接 = 当前 Windows 账户
```

实测（本机）：`DB_AUTH=trusted` 时连接身份是 `CQF\15392`，`IS_SRVROLEMEMBER('sysadmin') = 1`、`IS_MEMBER('db_owner') = 1`。

| 场景 | 建议 `DB_AUTH` | 数据库权限层是否生效 |
| --- | --- | --- |
| 日常开发 / 功能测试 / 演示点击 | `trusted` | **不生效**（全部连接都是 sysadmin） |
| 权限正/反例、列级收窄、`role_app` 口径等**证据** | `sql` | 生效（`scripts/verify_db_logins.py`、`dao_roles_test.py`、`order_pages_test.py --sql-auth` 均在此时生成证据） |

> 所以问“你们的受限账户真的在用吗”，答案要分两句：**默认启动用 `trusted`（方便）；权限相关证据一律在 `DB_AUTH=sql` 下跑**。
> 两份证据同时存在，不能拿 `trusted` 下的运行结果去证明受限账户有效。

数据库层对应角色：`login_clerk→role_cashier`、`login_customer→role_customer`（新建）、`login_maker→role_maker`、`login_stock→role_stock_keeper`、`login_manager→role_manager`；写事务另用 `login_app→role_app`（见 `sql/app_login.sql`）。

> **列级收窄（v1.0 追加）**：`role.sql`（第 4 周）给 `role_cashier` 的是 `shop_order` 的**整表 UPDATE**，
> 店员因此能直接写 `refund_amount`——与 `docs/01`“退款由店长审核”冲突。`app_login.sql` 在应用阶段把它
> 收窄为 **8 列**（`order_status, pay_method, pay_txn_no, paid_at, completed_at, item_subtotal,
> coupon_discount, total_amount`）；`refund_amount`/`refund_at`/`member_id`/`employee_id`/`created_at`
> 仍仅店长可写。实测：店员改 `refund_amount` → **230**，店长 → **OK**（T16/T17）。
> `role.sql` 原文保持不动（第 4 周证据），差异在此说明。

> `/health` 用 `manager` 连接统计结构指纹。复核时发现：`role_manager` 原来**没有** `item_material` 的
> `SELECT`，导致店长读库存报 229，而 236−216=20 恰好就是该表全部结构贡献（8 列 + 1 PK + 1 UQ +
> 7 CHECK + 3 DEFAULT）。早期版本用 `GRANT VIEW DEFINITION` 让 `/health` 数到 236，那只是"看得到元数据"，
> **功能上仍然 229**，属用权限掩盖缺口。现改为补足 `SELECT`（见 ⑤），`VIEW DEFINITION` 不再需要并已撤销。
>
> **写权限补缺（2026-10-21 交叉复核）**：`sql/app_login.sql` ⑧ 补了 maker 的 `item_material/order_platform`
> SELECT 与 `completed_at` UPDATE，新增 `role_app` 作为统一写事务账户（订单/库存/流水/会员/券写，无 DDL），manager 的余额/积分流水写；
> `DB_AUTH=sql` 下 7 组角色路径已实测 7/7 通过（见 §11）。

> **列级收窄的实际生效范围（2026-10-28）**：上表的 `role_cashier` 8 列、`role_maker` 2 列，只在“用该角色登录执行 SQL”时生效——
> 即**直连**，以及应用内走 `login_stock`/`login_manager` 的库存/商品写。应用内的**订单**写统一走 `role_app`（整表），不区分列；
> 详见 §10 的通道表与 §5.1 的 `trusted`/`sql` 差别。

> **下单权限在三层一致（2026-10-28 ④ 复核 P2-3）**：`order.create` 只给店员与顾客（上表），
> 业务层 `order_service._normalise_context` 的白名单同步收紧为 `{clerk, customer}`，页面层 `@role_required("order.create")`；
> 店长下单在**任一**层都是 403（此前服务层单独放行 manager，已收口）。平台单由**店员**录入。

## 10. 已知限制（记录，避免被当作缺陷）

- **顾客可自助下单，但写权限被切成"只能下单"**：`role_customer` 对 `shop_order`/`order_item`/
  `order_item_addon` 有表级 `INSERT`，对 `item_material` 只有 **列级 `UPDATE(reserved_qty)`**（改预占），
  `stock_qty` 等一律 **230**（已实测）。故"顾客改库存"在 DB 层就被挡。
  残留风险：表级 `INSERT` 意味着若应用层校验漏写，顾客身份可写任意形态的订单；行级隔离（只看自己的单、
  只改自己的预占）靠应用参数化，RLS 留 v2.0。**④ 的用例必须专门测"漏写 member_id 条件"。**
- **CSRF：v1.0 未做 token 校验（已知缺口）**：`requirements.txt` 只有 Flask/pyodbc，全库无 `CSRFProtect`/token；
  会话 cookie 设了 `HttpOnly`+`SameSite=Lax`，跨站 POST 不带 cookie，攻击面已被压低，但**不是完整的 CSRF 防护**。
  ⑤ 新增的支付/取消/退款/改状态四个表单同样没有 token（其中退款/取消涉及金额），与既有商品/库存表单口径一致。
  **v2.0**：接 Flask-WTF 的 `CSRFProtect` + 模板 `csrf_token()`。
- **登录凭据不在数据库**：v1.0 用配置内 demo 账号，见 §9。
- **订单号生成已定：应用层 `MAX+1`**（同一事务内取号并插入，撞 `2627` 重试），保住
  `YYYYMMDD + 4 位当日序号` 的"每日归零"口径；`SEQUENCE`/触发器仍留 v2.0。
- **P9（加料须属于该商品且为 ADDON）与 `size`/`product_id` 一致性**：数据库无跨表约束，由业务层校验（第六周已判定留 v2.0 触发器）。
- **顾客支付确认的连接角色**：`customer` 连接只负责“写订单三表 + 预占 `reserved_qty`”；支付确认、扣料、积分/余额/券核销由 `role_app` 写事务连接在同一事务内执行，符合“顾客写权限被切成只能下单”的口径。
- **role_app 写事务账户**：`login_app → role_app` 只用于下单/支付/扣料/会员/券写事务，无 DDL、无 GRANT、无 DELETE；应用层仍按 session 角色做权限矩阵校验。它不替代 5 个业务角色的读/权限演示，避免给 `role_cashier` 授予库存写权限而破坏权限矩阵。
  **推论（2026-10-28 ④ 交叉复核补充）**：既然写事务统一由 `role_app` 执行，第 4 周的“店员不能写 `refund_amount`”列级收窄
  **只对“绕过应用直连数据库”生效**，对经应用的写路径不再区分列（实测 `login_app` 可写 `refund_amount`，`login_clerk` 仍为 230）。
  所以“谁能退款”完全靠 `order_service.refund_order` 的 `role != "manager"` 判定 + 页面层 `order.refund` 权限点，DB 层不再兼管。
- **数据库权限到底在哪些通道上生效（2026-10-28 定稿口径）**：

  | 通道 | 用的登录 | DB 层管不管 | 依据/实测 |
  | --- | --- | --- | --- |
  | 应用内**订单**写（下单/支付/取消/退款/状态） | `login_app`（整表） | ❌ 不管列 | 跨 10 张表的单事务逼出来的（见下） |
  | 应用内**库存/商品**写 | `login_stock` / `login_manager` | ✅ 管 | `db_cursor("stock")` / `db_cursor("manager")` |
  | 绕过应用**直连**（sqlcmd/SSMS/pyodbc） | 任意角色登录 | ✅ 管（对象级 + 列级） | `result/第7周-①受限登录验证-*.txt` 17 项 |
  | 用 Windows 信任连接改库（跑 `sql/*.sql`、调试） | 当前 Windows 账户 = sysadmin | ❌ 完全不适用 | 属运维通道 |
  | **行级隔离**（只看自己的单） | 所有角色 | ❌ 任何情况都不管 | 实测 `login_customer` 能读全部 7 张订单；靠应用 `WHERE member_id=?`，RLS 留 v2.0 |

- **为什么必须有一个“万能”写账户**：一笔订单要在一份事务里写 `shop_order / order_item / order_item_addon / item_material / inv_stock_log / mkt_member_coupon / member_member / member_point_log / member_balance_log / order_platform` 共 10 张表；
  而按最小权限切出来的 5 个业务角色**没有任何一个能覆盖这 10 张表**（店员无库存/流水写、库存员无订单写、店长不能改库存、顾客只能改预占）。两条路：补权限（矩阵崩、T16/T17 作废）或造写事务账户 —— 选了后者。
  v2.0 若要收回这道区分，正统做法是把下单/退款写成存储过程 + `EXECUTE AS`（业务规则下沉到 T-SQL），或给“退款”单独用店长连接。
- **退券口径（2026-10-28 修正）**：`return_coupon` 把券退回 `UNUSED` 并清空 `used_order_id`（`docs/01` §4.4“退回为未使用，而非作废”）。
  代价：券与退款单的关联随之清空（退款单上的 `coupon_discount` 快照仍在），逐券审计使用史需 v2.0 的券使用流水表。
- **下单后改配方 → 取消/支付按新配方记账（2026-10-28 ④ 交叉复核 P1-2，v1.0 未彻底修复）**：
  `_usages_for_items` 用**当前**配方重算耗用，而预占是下单时按**旧**配方做的，且耗用量没有快照。实测三种后果：
  ① 预占不够 → 订单**卡在 `PENDING`**（既付不了也取消不了）——现统一报 `E4001` 并提示“配方可能已变更，请联系管理员处理”（不再误报 `E5003`“请重试”）；
  ② 配方变小 → 少扣/少释放，残留孤儿预占（可售虚低）；
  ③ 配方变大但有其它单预占兜底 → 静默多扣且 SALE 流水跟着多记。
  **触发面**：v1.0 页面没有配方维护入口（商品页只改名称/杯型/价/状态），`item_recipe` 只能直接改库，故仅改库/改 seed 时出现。
  **v2.0 前置条件**：① `order_item`（或新表 `order_item_usage`）快照每份用量，支付/取消读快照；
  ② 配方维护页必须**禁止在有 `PENDING` 订单的商品上改配方**。回归用例：`order_service_test.py` 的
  `test_cancel_after_recipe_changed_reports_business_rule` / `test_pay_after_recipe_changed_reports_business_rule`。

### 10.1 订单页面（⑤ Chen）的口径与取舍

- **平台单由店员录入，店长不能下单（三层已对齐）**：`docs/01` 的角色职责表把“收银台代录”归给收银员、
  “维护与审核退款”归给店长，因此 `permissions.PERMISSIONS` 不给 `manager` 以 `order.create`，
  `GET /orders/new`、`POST /orders/<id>/{pay,cancel}` 都用 `order.create` 把关（店长 403），
  **业务层 `_normalise_context` 也已收紧为 `{clerk, customer}`**（2026-10-28 ④ 复核 P2-3，
  此前服务层允许 manager，与矩阵不一致）。与测试用例 ORD-08“clerk1/平台入口”一致。
  若将来要让店长代班收银，**必须同时改三处**：矩阵 + `_normalise_context` 白名单 + `docs/01` 职责表。
- **券下拉怎么按会员号来（2026-10-28 ⑤ 复核补）**：GET 阶段按 URL 上的 `member_id` 列券，
  所以店员要么以 `GET /orders/new?member_id=C0000002` 进入，要么用页面顶部新加的“按会员号列券”GET 表单切换；
  下单表单里的“会员号”输入只影响**订单归属**，不会实时刷新券下拉（避免为一段下拉再引一轮 AJAX）。
- **券下拉：上界列券 + 页面 JS 置灰 + 服务端严判（2026-10-28 定稿）**：GET 阶段还不知道顾客会点几杯，
  算不出真实券前金额，所以 `order_service.list_usable_coupons` 按一个上界金额查询，**列出该会员有效期内未使用的券**；
  页面把每张券的门槛/优惠放进 `<option data-threshold data-discount>`，JS 按当前预估合计把尚未满门槛的券
  **置灰并标注“本单不满门槛”**（已选券变得不可用则退回“不使用”），选中可用券时额外显示“预计应付”。
  **服务端仍是唯一判定方**：`_apply_coupon` 按提交时的真实券前金额校验，不满足 → 409 `E4001`。
  性质：JS 只读页面数据、只改 DOM，不提交金额；关掉 JS 则全部券保持可选，只是少了提示。
  **v2.0 待办**：加 `quote`/预览函数（服务端真实算券前金额），把券下拉做成“精确可用券”并把预估应付算到服务端。
- **演示用券请走 C0000002（2026-10-28 定：不动 seed）**：seed 里 `C0000001` 的两张券分别是 `USED` 与历史
  `RETURNED`（不可用），`C0000002` 持有一张 `UNUSED` 的“满30减5”。演示链路：店员代客给 `C0000002`
  下单用券 → 取消 → 券回到 `UNUSED` → 再下一单仍可选同一张券（即 P1-1 修复后的行为）。
  **不改 `02-seed.sql`**：加券会让样例数据 127→128 行，连带第 3 周 ④/⑥ 两份证据（含数据指纹 SHA256）
  与多份文档的历史数字全部重跑；若现场必须演示“顾客自助用券”，用一条临时 `INSERT` 发券即可，不进仓库。
- **成功 302，失败回填重渲染（2026-10-28 定，参照 WTForms / Rails 的做法）**：写操作成功后 302 到详情页
  （POST-Redirect-GET，刷新不重复下单）；**表单类错误**（`E1001` 参数、`E4001` 业务规则、`E3001` 资源不存在、
  `E5002` 约束冲突）由页面层就地回填重渲染同一张表单，状态码仍取错误的 HTTP 码，用户不必重填（含杯数、
  糖冰温、加料、券、会员号、平台字段）；**其余错误**（`E2003` 无权限、`E5001` 库不可用、`E5003` 事务失败、
  `E9001` 内部错误）继续交给全局异常处理器渲染错误页，避免把系统故障当成表单错误。
  代价：失败时 URL 仍是 `POST /orders/`（刷新会重发，但只会得到同一个 4xx，无副作用）。
  已知细节：`<input type="number">` 里回填**非数字**值（如 `abc`）时，HTML 会把这个值丢掉、输入框显示为空——
  这是浏览器的固有行为（HTML 属性里有 `value="abc"`，但渲染为空）；其余字段照常回填。
  实现：`order_routes._form_context()` 供 GET 首渲染与 POST 回填共用；`_FORM_LOCAL_ERRORS` 是白名单；
  回填错误的明细仍按 `rid` 写日志（全局处理器不经手，故页面层自己记一份）。
- **`/orders/mine` 对店员（有 `order.read_own` 但账号不绑会员）返回空列表 + 提示**，不报 403：
  他没有可看的“自己的单”，但也不该因缺数据被报错。
- **下单表单只认服务端查到的商品与其可用加料**：表单里多塞的 `product_id`/加料字段被丢弃（不会报错），
  金额、库存是否充足、加料是否属于该商品全由业务层重算/校验。
- **金额预览是页面内联 JS**，只做提示、不提交任何金额字段；关闭 JS 只是不显示预估合计，不影响下单。
