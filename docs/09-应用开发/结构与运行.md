# 第七至九周：应用分层结构与运行

> 对应步骤 **①（确认 v1.0 基线与运行环境）** 与 **②（搭建分层项目骨架）**。
> 目标：在 v1.0 数据库（结构指纹 **236**）之上，按「页面层 → 业务层 → 数据访问层 → 数据库层」构建可运行、可复现的 Web 应用。

## 1. 运行环境（① 的结论）

| 项 | 值 |
| --- | --- |
| 语言与框架 | Python **3.13.12** + Flask **3.1.3**（Jinja2 模板） |
| 数据库驱动 | **pyodbc 5.3.0** + **ODBC Driver 18 for SQL Server**（已装 17/18） |
| 数据库实例 | SQL Server **17.0.1000.7 Express**，实例名 `.\SQLEXPRESS` |
| 应用库 | **`MilkTeaShop_v01`**（第六周迁移后的 **v1.0**，236 项指纹） |
| 认证方式 | 实例已开启**混合模式**（2026-10-18，`IsIntegratedSecurityOnly=0`）；应用默认 `DB_AUTH=trusted`，可切 `sql`（5 个受限登录） |
| 说明 | `MilkTeaShop_v01` 中的 `_v01` 指"迁移副本"，**它本身是 v1.0**，不是 v0.1；v0.1 源库为 `MilkTeaShop`（219 项），应用不连它 |

## 2. 分层结构与职责

| 层 | 目录 | 负责 | 不应承担 |
| --- | --- | --- | --- |
| 页面层 | `app/pages/`、`app/templates/` | 接收请求、表单基础校验、渲染页面、返回统一响应 | 不直连数据库、不拼 SQL、不决定数据库权限 |
| 业务层 | `app/services/` | 业务规则、角色可执行范围、事务边界、异常归类 | 不把原始数据库异常返回前端 |
| 数据访问层 | `app/dao/` | 参数化 SQL、连接/游标/事务/释放、结果映射 | 不接收模板逻辑、不拼接用户输入 |
| 数据库层 | SQL Server `MilkTeaShop_v01` | 表、约束、视图、角色与权限 | 不依赖页面隐藏按钮保证安全 |

横切（不属于某一层）：`app/config.py` 统一配置、`app/errors.py` 统一错误码与日志。

## 4. 两条调用链（任务要求能讲清）

```text
查询（GET /products/）：
  浏览器 → main/product 蓝图（role_required 校验）→ services.permissions 判定权限
        → dao.db_cursor()（按角色取连接）→ 参数化 SELECT → SQL Server
        → 结果映射 → 模板渲染 / 统一 JSON → 浏览器

修改（下单，步骤 ④ 落地）：
  浏览器提交 → 页面层基础校验 → services 业务规则（库存充足、状态可改、明细合法）
            → dao.db_cursor(commit=True) 同一事务写 shop_order + order_item
              + order_item_addon + 库存预占/扣减 + inv_stock_log
            → 提交或回滚 → 统一响应 → 浏览器
```

## 5. 配置项（`app/config.py`）

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `SECRET_KEY` | `dev-only-change-me` | Flask session 签名；演示前请改随机串 |
| `DB_AUTH` | `trusted` | `trusted` = Windows 信任连接；`sql` = 按角色用受限 SQL 登录 |
| `DB_SERVER` | `.\SQLEXPRESS` | 实例名 |
| `DB_NAME` | `MilkTeaShop_v01` | 必须是 v1.0 库（236） |
| `DB_DRIVER` | `ODBC Driver 18 for SQL Server` | 已装 17/18，任选其一 |
| `DB_TIMEOUT` | `5` | 连接超时（秒） |
| `USER_STORE` | `config` | `config` = demo 账号；`db` = v2.0 的 `app_user` 表 |
| `DB_PWD_LOGIN_*` | 空 | `DB_AUTH=sql` 时每个登录的密码 |
| `APP_HOST` | `127.0.0.1` | 监听地址（仅 `run.py` 使用） |
| `APP_PORT` | `5000` | 监听端口 |
| `APP_DEBUG` | `0` | 置 `1` 开 Flask 调试（仅本地开发） |

> 以上均可在 `.env` 中设置；`.env` 在**仓库根目录**，不依赖启动时的 cwd。
> `DB_AUTH` / `USER_STORE` 写错会在启动时直接报错（不静默降级）。

数据库层对应角色：`login_clerk→role_cashier`、`login_customer→role_customer`（新建）、`login_maker→role_maker`、`login_stock→role_stock_keeper`、`login_manager→role_manager`（见 `sql/app_login.sql`）。

> **列级收窄（v1.0 追加）**：`role.sql`（第 4 周）给 `role_cashier` 的是 `shop_order` 的**整表 UPDATE**，
> 店员因此能直接写 `refund_amount`——与 `docs/01`“退款由店长审核”冲突。`app_login.sql` 在应用阶段把它
> 收窄为 **8 列**（`order_status, pay_method, pay_txn_no, paid_at, completed_at, item_subtotal,
> coupon_discount, total_amount`）；`refund_amount`/`refund_at`/`member_id`/`employee_id`/`created_at`
> 仍仅店长可写。实测：店员改 `refund_amount` → **230**，店长 → **OK**（T16/T17）。
> `role.sql` 原文保持不动（第 4 周证据），差异在此说明。

> `/health` 用 `manager` 连接统计结构指纹。复核时发现：`role_manager` 原来**没有** `item_material` 的
> `SELECT`，导致店长读库存报 229，而 236−216=20 恰好就是该表全部结构贡献（8 列 + 1 PK + 1 UQ +
> 7 CHECK + 3 DEFAULT）。早期版本用 `GRANT VIEW DEFINITION` 让 `/health` 数到 236，那只是"看得到元数据"，
> **功能上仍然 229**，属用权限掩盖缺口。现改为补足 `SELECT`（见 ⑤），`VIEW DEFINITION` 不再需要并已撤销。

## 9. 与 v2.0 的衔接

v1.0 不新增表（保持 236）：登录凭据放在 `app/demo_users.py`，隔离在 `UserStore` 接口之后。
v2.0 通过 `migration_v2_0.sql` 新增 `dbo.app_user`（用户名、密码哈希、角色、会员/员工绑定），
把 `USER_STORE` 改为 `db` 即切换到 `DbUserStore`，**业务代码与页面零改动**。

## 10. 已知限制（记录，避免被当作缺陷）

- **顾客可自助下单，但写权限被切成"只能下单"**：`role_customer` 对 `shop_order`/`order_item`/
  `order_item_addon` 有表级 `INSERT`，对 `item_material` 只有 **列级 `UPDATE(reserved_qty)`**（改预占），
  `stock_qty` 等一律 **230**（已实测）。故"顾客改库存"在 DB 层就被挡。
  残留风险：表级 `INSERT` 意味着若应用层校验漏写，顾客身份可写任意形态的订单；行级隔离（只看自己的单、
  只改自己的预占）靠应用参数化，RLS 留 v2.0。**④ 的用例必须专门测"漏写 member_id 条件"。**
- **登录凭据不在数据库**：v1.0 用配置内 demo 账号，见 §9。
- **订单号生成已定：应用层 `MAX+1`**（同一事务内取号并插入，撞 `2627` 重试），保住
  `YYYYMMDD + 4 位当日序号` 的"每日归零"口径；`SEQUENCE`/触发器仍留 v2.0。
- **P9（加料须属于该商品且为 ADDON）与 `size`/`product_id` 一致性**：数据库无跨表约束，由业务层校验（第六周已判定留 v2.0 触发器）。
