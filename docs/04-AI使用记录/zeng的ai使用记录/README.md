# zeng 的 AI 使用记录

> 课程要求：允许用大模型，但须保留**提示词、候选答案、人工修改与验证证据**；AI 结果不能替代 SQL 测试、约束验证和答辩。

## 我的用法：AI 放在"铺开选项"和"施工"两个位置，判断权不外放

第 3 周我负责**建库与建表**（步骤 ①②④）。这周的产出要同时站得住三条：**能跑通、能复现、能被组员接手**。三条都不是"把 `docs/02` 翻译成 SQL"能自动满足的——翻译可以一字不错却依然不能用。

所以我只把 AI 用在这两个位置：**铺开选项**（把每条路的代价、边界、失败模式摆出来，而不是直接给答案）和**当施工队**（写脚本、跑实测、算我不可能手工验证的数字）。**定边界、拍判断、验收证据**这三件事不外包。

全周真正耗神的不是写 SQL，而是下面四条判据的反复套用：

| # | 我的判据 | 一句话说明 |
| --- | --- | --- |
| 1 | **公共约定不私下拍板** | 问"改它要牵动几个人"。牵动多人的量，不能由一个人先定 |
| 2 | **破坏性脚本要比"能跑"更高一档** | "能删掉"和"敢让它删"是两件事，后者要求可解释、可防护、可复现 |
| 3 | **文档与实现只能有一个版本** | 一旦冲突，先判"哪边是对的"，再两边一起改；绝不就地改脚本了事 |
| 4 | **证据必须可证伪** | "一致""通过"只有在**它有可能失败**的前提下才算证据，否则只是自我安慰 |

## 第 3 周：建库与建表（`sql/00-create.sql`、`sql/01-schema.sql`，步骤 ①②④）

> 本周是**第一次真的跑 SQL**。前两周的产出全是判断，本周开始有客观反馈：类型不符、外码不存在、约束被违反都会当场报错。我的态度是——**先对齐再动手，且不接受"看起来对"**。

### 3.1 建库：六个决策

**决策 1｜库名和排序规则不由我一个人定**

- **岔路**：我先定一个名，组员后面跟着改 ／ 先确认再动手。
- **判据**：判据 1。库名会被 `01-schema.sql` 的 `USE`、`role.sql`、以及**每个人的 sqlcmd 命令**同时引用——它不是我的私有变量，是全组的公共标识。
- **定案**：动手前先确认：库名 `MilkTeaShop`，排序规则**显式**写 `Chinese_PRC_CI_AS`。
- **已验证**：此后库名从未返工；Chen 在另一台实例（`CQF\SQLEXPRESS`）上复核，拿到的库与我的完全一致——**显式排序规则正是"换台机器还能复现"的前提**，若继承实例默认值，换台默认值不同的实例这条要求直接不成立。

**决策 2｜"建库"到底该做什么——把"复现"定义清楚**

- **岔路**：库不存在时才创建 ／ 每次都先删后建。
- **判据**：判据 4。`01-schema.sql` 与 `02-seed.sql` **只能在空库上跑**（表已存在会报错、数据重复会撞约束）。若只在不存在时创建，第二次复现必然失败。
- **定案**：每次都先删后建，把本脚本的职责定位为"**把库恢复成空库起点**"。并明确"复现"的口径——**删掉库、从头跑完、得到同样的表结构与数据**，而不是"在已有库上不报错地再跑一遍"。
- **已验证**：这条口径被写进 `sql/README.md` 成为全组共识：复现前无需任何人工清理，直接重跑即可。

**决策 3｜删库前必须强制断开占用连接**

- **岔路**：直接 `DROP DATABASE` ／ 先 `SET SINGLE_USER WITH ROLLBACK IMMEDIATE` 再 `DROP`。
- **判据**：判据 2。这是删库操作，"失败"和"半途失败"的代价不同——不能靠运气。
- **定案**：先强断连接再删。
- **已验证（双向实测）**：**反证**——起一个会话占住该库后裸 `DROP`，当场报 `Cannot drop database "MilkTeaShop" because it is currently in use`；**正证**——加上 `SINGLE_USER` 后脚本正常完成。这一行不是保险，是**必需**。

**决策 4｜破坏性操作的防护要分层，且不写死任何别人机器上没有的东西**

- **岔路**：删库脚本只写删库 ／ 加防护。
- **判据**：判据 2。这是**全组共用实例**上的不可逆操作，一次手滑没有第二遍。
- **定案**：四层防护一起上——
  1. `USE master` 前置（`DROP DATABASE` 删不掉"当前所在的库"，否则组员用 `-d` 跑就会失败）；
  2. **系统库名守卫**：库名若为 `master`/`tempdb`/`model`/`msdb`/`distribution` 或为空，`THROW` 直接中止；
  3. **不写死 `.mdf`/`.ldf` 路径**，让各人机器用实例自己的默认目录（写死 `C:\...` 会让脚本在别人机器上直接失败）；
  4. 库名只声明一次 + **切库后用 `DB_NAME()` 自检两处库名是否一致**，专门抓"改库名改漏一处"。
- **已验证**：把库名误改成 `master` 后执行 → `THROW 51001` 中止、`exit=1`，`master`/`tempdb`/`model`/`msdb` 四个系统库完好无损。

**决策 5｜治理"反复删建"的副作用**

- **岔路**：用实例默认恢复模式 ／ 建库后设 `RECOVERY SIMPLE`。
- **判据**：本周要反复"删库→重建→装载"，完整恢复模式会持续堆积事务日志直到占满磁盘；课堂项目不需要时间点恢复能力。
- **定案**：建库后显式 `ALTER DATABASE … SET RECOVERY SIMPLE`，作为建库脚本的固定收尾设置。
- **已验证**：作为脚本固定收尾步骤执行，与删库、建库同批完成。

**决策 6｜输出必须能当证据，且换客户端也要一样**

- **岔路**：脚本跑完就算完 ／ 让脚本自己输出可留档的确认信息。
- **判据**：判据 4。证据要能回答"**谁、在哪个实例上、什么时候、建出了什么**"，否则 `result/` 里的输出无法被独立核对。
- **定案**：
  - 收尾输出确认表：库名 + 排序规则 + 状态 ／ 实例名 + 版本号 ／ 执行者登录名 + 时间戳；
  - 消息前缀避开方括号——实测 **sqlcmd 会把行首 `[..]` 连同内容一起吞掉**（连 `-o` 写文件也一样），证据里只剩半句话；
  - **不依赖任何 sqlcmd 专有语法**（如 `:setvar`），使脚本在 SSMS 里也能直接跑。
- **已验证**：同一份脚本，走 `sql/README.md` 的 sqlcmd 命令与在 SSMS 里直接执行，**两条路都跑通**。

### 3.2 建表：八个决策

**决策 7｜建表顺序按外码拓扑序，而不是按文档的表序号**

- **岔路**：照 `docs/02` §2.2 的表序号 `1→17` 建 ／ 按外码依赖排批次。
- **判据**：判据 4。顺序错了不是"返工"，是**根本跑不起来**——外码指向的表必须先存在。
- **定案**：按 `docs/06` §二 的外码拓扑序分 10 个批次建，与 `docs/02` 的表序号解耦。
- **已验证**：17 张表一次顺序执行全通；建成的 **25 条外码**与 `docs/02` §3.1 的 25 行关联双向零差异。

**决策 8｜本轮建多少、怎么切——按"外码封闭的域"切，不按序号取前缀**

- **岔路**：按表序号取前 N 张 ／ 按外码封闭的业务域切。
- **判据**：判据 4。切出来的东西必须**能被独立验证**。序号前缀的外码会指向尚未创建的表，根本跑不起来；而按域切，外码只互相指向，可以独立跑通、独立装载、独立复现。
- **定案**：先建**商品/原料域 4 张**（`item_product`/`item_material`/`item_recipe`/`item_addon_option`），用仓库里**真实的 `02-seed.sql`** 对应段落做装载验证；随后按拓扑序补齐至 17 张。
- **已验证**：4 张表独立跑通并吃下真实 seed（5/7/23/5 行）。**事后看，本轮 5 处缺陷里有 4 处在这个阶段就已暴露**——这正是"用最小可验证单元先打通链路"的价值：把"能不能跑通"和"表建全了没有"拆成两个问题，前者早验证早暴露。
- **附带决策**：验证数据一律用**仓库里的真实 seed**，不另造测试数据——自造的测试数据证明不了 seed 能用。

**决策 9｜约束必须显式命名——这不是风格问题，是复现的硬要求**

- **岔路**：`CHECK`/`DEFAULT` 不命名，交给 SQL Server 自动起名 ／ 全部显式命名。
- **判据**：判据 4。不命名的约束会拿到 `DF__item_pro__sale___1A2B3C4D` 这类**带随机十六进制后缀**的名字，两次复现建出的约束名就不一样——"**得到相同的表结构**"这条要求当场不成立。
- **定案**：在 `docs/06` §五 已有的 `PK_表名`/`FK_子表_父表`/`UQ_表名_字段名` 之外，**延伸出** `CK_表名_字段名`、`DF_表名_字段名` 两类，并把"为什么必须命名"的理由写在脚本头部。
- **已验证**：结构指纹把**约束名与定义一起**纳入比对（16 条 DEFAULT + 36 条 CHECK 逐条按名比对），两遍复现 SHA256 完全相同——**约束名确实稳定**。

**决策 10｜可空候选码：改实现，不改口径**

- **岔路**：用 `UNIQUE` 约束 ／ 改文档放弃"多 NULL" ／ 换一种实现。
- **判据**：判据 3。冲突的是**实现**与**口径**，而口径（`docs/02` §5.2"可空，多 NULL 不冲突"）是业务真需要的：现金单、余额单、平台单都没有支付流水号，它们必须能共存。**错的是实现，不是口径。**
- **定案**：三列（`shop_order.pay_txn_no`、`member_member.phone`、`member_balance_log.external_ref`）改用**带筛选条件的唯一索引** `CREATE UNIQUE INDEX … WHERE 列 IS NOT NULL`——这才是"唯一、但允许多个 NULL"在 SQL Server 里的正确实现，**`docs/02` 一个字都不用动**。
- **已验证**：7 张订单（其中 3 张非线上单、`pay_txn_no` 均为 `NULL`）全部装载成功。此前用 `UNIQUE` 约束时报的是 `Violation of UNIQUE KEY constraint … The duplicate key value is (<NULL>)`——**等于全库只能存在一张非线上订单**，这是结构性缺陷，不是数据问题。
- **连带决策**：筛选索引要求 DML 时 `QUOTED_IDENTIFIER`/`ANSI_NULLS` 为 ON，而 **sqlcmd 默认 OFF、SSMS 默认 ON**。为守住"换客户端同结果"，在两个脚本内**显式 `SET` 写死**，不依赖任何客户端默认值。

**决策 11｜删除规则的两种语义要分开：弱实体级联，审计流水不级联**

- **岔路**：所有外码统一加 `ON DELETE CASCADE` ／ 统一都不加 ／ 按业务语义分。
- **判据**：问"**父行的消失，该不该带走子行**"。`order_item`/`order_item_addon`/`order_platform` 是**弱实体**——订单没了，它们本就是订单的一部分，应随之消失；而三类流水（库存/积分/余额）是**审计依据**，对应的原料或会员即便停用，流水也必须留下。
- **定案**：三张弱实体表的外码加 `ON DELETE CASCADE`（依据 `docs/02` §3.3）；流水表外码一律**不加**级联。
- **推论（有意为之的代价）**：因此**有流水的订单删不掉**——这不是缺陷，是"流水必须保留"的必然结果。复核方向 A 也正好建议把这一点补写进 `docs/02` §3.3，避免后来者当成 bug。

**决策 12｜`CHECK` 的取舍口径：列级本周写齐，行级跨列留第 4 周**

- **岔路**：本周只写列级约束 ／ 本周把跨列约束也写全。
- **判据**：当时我引的是 `docs/06/第二周 §六.8` 末段"属第 4 周""此处仅记录这是一条约束，不写 SQL"。
- **定案**：列级（枚举取值 + `> 0`/`>= 0` 取值范围）本周写进 `01-schema.sql`；行级跨列（如 `reserved_qty <= stock_qty`）留第 4 周。
- **结果与自评——这条我判错了一半**：列级部分是对的；但**跨列部分是对 `§六.8` 的过度推广**——那句原文只针对**一条具体约束**说"属第 4 周"，并未给出"跨列就推后"的整类规则；而第三周任务讲解 §2 明写本周就要"设置…检查约束"、未区分列级/跨列。**把一条具体结论推广成整类规则，是引用文档时最容易犯的错。** 这一条被步骤 ③ 的独立复核推翻后，本周一并补写了 9 条跨列 CHECK（扩到 45 条），并给 §六.8 那句加了"第 3 周修正"标注。
- **我记下这条，是因为它对我不利**：那是**我基线上的错判**，而且我在过目 AI 输出时放过了它。复核把它拦下来，正说明**产出者自查存在系统性盲区**——这也是 `docs/05` 协作约定里"复核的意义在换一双眼睛"的实证。

**决策 13｜用 `CHECK` 表达"条件性约束"时，依赖 NULL 的求值语义**

- **岔路**：为"平台单没有 `order_mode`""未付款没有 `pay_method`""不管控效期"各写一条带 `IS NULL OR …` 的复杂条件 ／ 直接用普通 `IN` 枚举。
- **判据**：我要的是"**有值时必须合法，没值时放行**"。T-SQL 里 `CHECK` 对 `NULL` 求值为 `UNKNOWN`，而 `UNKNOWN` **不拦截**——这恰好就是条件性约束想要的语义。
- **定案**：`order_mode`、`pay_method`、`shelf_life_days` 直接写普通枚举/范围 `CHECK`，**不额外写 `IS NULL OR …`**，只在注释里说明"NULL 放行"是有意为之。
- **已验证**：平台单（`order_mode = NULL`）、待支付单（`pay_method = NULL`）、不管控效期的原料（`shelf_life_days = NULL`）全部正常装载——**用最少的写法拿到了正确的语义**。

**决策 14｜让自检数字能被文档的独立来源对账**

- **岔路**：自检只打印"建表完成" ／ 输出可与 `docs/02` 对账的结构统计。
- **判据**：判据 4。一个**只能通过**的自检等于没有自检。数字必须有两个独立来源——一边来自运行中的数据库，一边来自 `docs/02`，对不上就说明有问题。
- **定案**：自检输出两段——逐表的（列数 / 主码 / 外码 / CHECK / 默认值 / 候选码），加一段汇总；并在脚本末尾附上"**本脚本故意没写的 3 项及原因**"，把"有意不做"和"忘了做"明确区分开。
- **已验证**：汇总 **17 表 / 25 外码 / 36 CHECK / 16 默认值 / 17 主码 / 6 候选码**，与 `docs/02` 的三个独立来源逐项对上——§3.1 有 25 行关联、§5.2 有 6 张表有候选码、17 张表 17 个主码；另用负向自检（非空库重跑被拦住、`exit=1`）证明这个自检**会失败**。汇总口径也曾算错一次（`sys.indexes` 含系统内部表索引，数出 170），修正为限定用户表——**正因为有文档这个独立来源，我才发现数字不对**。

### 3.3 我如何验收 AI 的输出

AI 写得很快，但**快不等于合格**。我形成了一套固定的审查维度，每个维度问一个问题，答不上来就退回重做：

| 审查维度 | 我问的问题 |
| --- | --- |
| 语义正确性 | 它符合业务口径，还是只符合字面？ |
| 跨工具一致性 | 在 sqlcmd 和 SSMS 里结果一样吗？ |
| 归因准确性 | 它给出的因果解释，真的成立吗？ |
| 统计口径 | 这个数字能被 `docs/02` 的**独立来源**对上吗？ |
| 表达可读性 | 下一个人接手时，看得懂吗？ |
| 证据可证伪性 | 这个"通过"有可能失败吗？ |

按这套维度被打回或修正的 7 处：

| # | 维度 | AI 的产出 / 说法 | 我凭什么认定它不合格 | 我的处置 |
| --- | --- | --- | --- | --- |
| 1 | **归因准确性** | "删库会强制断开**组员**的连接" | 我追问"为什么会有组员会话？我们好像没建连接"，它承认那个会话是**它自己造的测试替身**；本机是单机 Express，组员物理上连不到。**把测试口说成真人，结论的可信度就没了** | 更正为准确表述：最常见的占用者是**自己的 SSMS 对象资源管理器**；只有全组共用实例时组员连接才会被强杀 |
| 2 | **证据可证伪性** | 复现验证报告"两遍结构与数据指纹哈希一致" | 我要把证据看清楚——**指纹文件里只装了一行排序规则报错**，两遍"一致"只因都是同一条错误，这个"通过"**根本没有失败的可能** | 重做：给目录视图字符串列加 `COLLATE DATABASE_DEFAULT`，并加断言"文件里不得有 `Msg ` 报错行"。重做后指纹 210 条 / 数据 68 行、零报错、两遍 SHA256 相同 |
| 3 | **语义正确性** | `item_material.unit` 定为 `VARCHAR(10)` 且无取值约束 | `02-seed.sql` 里该列存的是**中文**（`N'克'`/`N'毫升'`/`N'个'`），`VARCHAR` 存中文受库排序规则影响、可能乱码 | 改 `NVARCHAR(10)` 并加 `CK_item_material_unit`；同轮发现 §1.1 枚举表**漏登 `item_product.size`**（与 `order_item.size` 同域），补成两字段同域 |
| 4 | **跨工具一致性** | 报错 `Msg 1934: … SET options … 'QUOTED_IDENTIFIER'` | 同一脚本**在 SSMS 能跑、按 README 的 sqlcmd 命令不能跑**——"换工具就变结果"直接违背复现要求 | 脚本内显式 `SET QUOTED_IDENTIFIER ON; SET ANSI_NULLS ON;`（见决策 10 连带项） |
