## 一、基线

| 既有审计表 | 无 |

现有库存写入路径（第十周已收口，是本周唯一事实来源）：

| 路径 | 代码位置 | 库存效果 | 业务流水 |
| --- | --- | --- | --- |
| 预占 / 释放 | `dao/inventory.reserve_stock` / `release_reserved` | 只改 `reserved_qty` | 不写 |
| 支付确认耗用 | `confirm_order_stock` | 减 `reserved_qty` + 减 `stock_qty` | 每原料一条 `SALE` |
| 平台/现金直接扣减 | `deduct_order_stock` | 减 `stock_qty` | 每原料一条 `SALE` |
| 库存调整 | `usp_adjust_stock` | 改 `stock_qty` | 一条 `GAIN/SHORT/LOSS` |
| 补货验收 | `receive_restock` | 加 `stock_qty` | 一条 `IN` |

结论：**业务流水已有唯一写入者**（DAO 或过程），本周触发器不能再写 `inv_stock_log`，
否则 `SALE`/`IN` 会被重复记账，且触发器无法从 `item_material` 行反推订单号/补货单号。

## 二、库存审计触发器（②）

### 2.1 审计表与业务流水分离

新增 `dbo.inv_stock_audit`（迁移 `sql/migration_v2_3_audit.sql`，版本 **2.3**）：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `audit_id` | `BIGINT IDENTITY` PK | 代理键 |
| `material_id` | `CHAR(8)` NOT NULL | 原料编号（**不建外码**：主数据删除后历史审计仍须保留） |
| `before_qty` | `DECIMAL(10,2)` NOT NULL | 变动前现存量 |
| `after_qty` | `DECIMAL(10,2)` NOT NULL | 变动后现存量 |
| `change_qty` | 计算列 `after_qty - before_qty` PERSISTED | 变化量（正增负减） |
| `change_type` | `VARCHAR(10)` CHECK `INSERT/UPDATE/DELETE` | 事件类型 |
| `operator_id` | `VARCHAR(128)` NULL | 员工编号（仅当会话上下文命中 `staff_employee`） |
| `operator_source` | `VARCHAR(10)` CHECK `SESSION/LOGIN` | 操作人来源；不允许空 |
| `login_name` | `NVARCHAR(128)` NOT NULL | 实际数据库登录（`SUSER_SNAME()`） |
| `changed_at` | `DATETIME2(0)` NOT NULL DEFAULT `SYSDATETIME()` | 变动时间 |

索引：`IX_inv_stock_audit_material_time (material_id, changed_at DESC)`。

`inv_stock_audit` 只回答「谁在什么时候把哪个原料的现存量从多少改到多少」；
`inv_stock_log` 继续回答「这笔变动属于哪张订单/哪张补货单」。两者职责不重叠。

### 2.2 事件矩阵

| 事件 | 记录条件 | before | after | change_type |
| --- | --- | --- | --- | --- |
| INSERT | 任意新增原料 | 0 | `stock_qty` | `INSERT` |
| UPDATE | **仅 `stock_qty` 发生变化** | `deleted.stock_qty` | `inserted.stock_qty` | `UPDATE` |
| DELETE | 任意删除原料 | `stock_qty` | 0 | `DELETE` |

- `reserved_qty` 的预占/释放不是库房实存变动，**不记审计**；这也避免顾客下单路径产生噪声审计。
- 多行语句按 `inserted`/`deleted` 集合处理：一条 UPDATE 改 N 行写 N 条审计，行间靠 `material_id` 对应。
- 触发器为 `AFTER`，与业务写入同一事务；触发器内 `THROW` 会把事务标记为不可提交（`XACT_STATE=-1`），
  由调用方整体回滚，因此多行语句不会留下部分审计或部分完成。

### 2.3 操作人传递

触发器没有参数，操作人按以下优先级确定：

1. 应用在每次写库存前设置会话上下文：`EXEC sys.sp_set_session_context @key=N'employee_id', @value=?`；
2. 触发器读 `SESSION_CONTEXT(N'employee_id')`，仅当它是 `staff_employee` 中存在的 8 位员工编号时采用，
   `operator_source='SESSION'`；
3. 否则退回 `SUSER_SNAME()` 作为 `login_name`，`operator_id=NULL`、`operator_source='LOGIN'`。
   **不阻断写入**：直接 sqlcmd/运维脚本没有会话上下文，仍须能改库存；但不能伪造出「员工已确认」。

应用接入点（② 一并改）：

| DAO 函数 | 传入的员工 |
| --- | --- |
| `adjust_stock_v2` / `adjust_stock_with_log` | 页面会话的 `employee_id` |
| `confirm_order_stock` | 当前收款员工。顾客支付使用数据库登录名 |
| `deduct_order_stock` | 下单员工 |
| `receive_restock` | 验收员工 |

`reserve_stock` / `release_reserved` 不设置上下文（不写审计）。

### 2.4 权限

触发器以调用者身份执行，因此：

- `role_app`（写事务账户）与 `role_stock_keeper`（库存调整/验收账户）需要 `INSERT` + `SELECT` 于 `inv_stock_audit`；
  触发器还要用会话员工编号校验 `staff_employee`，因此这两个角色同时需要 `staff_employee` 的 `SELECT`
  （缺它会在 SQL 认证下让每次库存写入报 229）；
- `role_manager`、`role_stock_keeper` 需要 `SELECT`（审计查询/报表）；
- `role_customer` 只更新 `reserved_qty`，触发器在进入 INSERT 前提前 `RETURN`，不要求该表权限；
  ⑤ 必须用 `role_customer` 实跑一次「下单预占」证明不被权限拦住。

## 三、订单完成规则触发器（③）

事件：`shop_order` 的 `AFTER INSERT, UPDATE`。直接插入已完成单和改写已完成单的完成时间均被拒绝。

| 编号 | 规则 | 错误 |
| --- | --- | --- |
| C1 | 只允许 `MAKING → COMPLETED`；`PENDING/PAID/CANCELLED/REFUNDED → COMPLETED` 拒绝 | 51112 |
| C2 | 已是 `COMPLETED` 又重写 `completed_at`（重复完成）拒绝；`SET order_status = order_status` 这类纯 no-op 放行，避免权限矩阵的空更新被误伤 | 51111 |
| C3 | `completed_at` 必填且不早于 `paid_at`；`paid_at` 必填 | 51113 |
| C4 | 订单至少一条明细；所有明细 `qty > 0`、`unit_price >= 0`，商品存在（外码已保证） | 51114 / 51115 |
| C5 | `total_amount = item_subtotal − coupon_discount` 且 `item_subtotal = Σ(qty×unit_price) + Σ(加料份数×addon_price快照)` | 51116 |
| C6 | 该单已有支付扣料证据：存在 `SALE` 流水；若同时有 `order_material_usage`，每条耗用都要有同原料、同数量的 `SALE` 流水 | 51117 |

- **不重复扣库**：触发器只校验，不做任何 `UPDATE item_material`；支付时已扣料，完成不能再扣一次。
- **不拒历史快照**：不比较 `order_item.size` 与 `item_product.size`，商品后来改杯型/改名不影响历史订单完成。
- **多行**：所有检查用 `EXISTS ... FROM inserted JOIN deleted` 集合判断；任一行非法即 `THROW`，
  事务被标记为不可提交、由应用整体回滚，合法行也不会被提交（⑤ 先提交两单夹具，再做非法混合 UPDATE，
  回滚后核对两单仍为 `MAKING`）。
- 其它状态流转（`PENDING→PAID`、`PAID→MAKING`、`→REFUNDED`、`→CANCELLED`）不归本触发器管，保持现有服务层规则。

## 四、三类窗口查询（④）

落点 `sql/window_query.sql`：三个内联表值函数 + 三条演示 `SELECT`（函数是唯一口径来源，测试直接调函数）。

| 简称 | 函数 | 窗口 | 业务含义 |
| --- | --- | --- | --- |
| W1 | `dbo.fn_product_sales_rank(@from,@to)` | `RANK() OVER (ORDER BY SUM(qty) DESC)`、`DENSE_RANK() OVER (ORDER BY SUM(qty*unit_price) DESC)` | 商品销量排名；并列用 RANK（并列后跳号），金额排名用 DENSE_RANK 供对照 |
| W2 | `dbo.fn_daily_sales_cumulative(@from,@to)` | `SUM(...) OVER (ORDER BY sale_date ROWS UNBOUNDED PRECEDING)` | 按自然日累计销量/销售额，无销售日补 0，便于看累计曲线 |
| W3 | `dbo.fn_daily_sales_moving_avg(@from,@to)` | `AVG(...) OVER (ORDER BY sale_date ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)` | 最近 **3 个自然日**移动平均，含无销售日（0 计入），不是「最近 3 笔」 |

统一口径沿用第十周 D1/D2：时间字段 `created_at`、闭区间含结束日；只算 `PAID/MAKING/COMPLETED`。
自然日骨架用「数字辅助表 + DATEADD」生成，**不用递归 CTE**——递归查询是第十二周任务，本周不提前占用。

## 七、边界与已知取舍

1. **历史待支付单**：v2.1 之前创建且无耗用快照的单，支付/取消仍按既有策略人工核对；完成触发器只要求
   `SALE` 流水存在，因此不影响历史已完成单。
2. **审计无外码**：原料/员工被删后审计仍保留原始编号，查询时左连接主数据即可显示名称；不以级联删除牺牲审计。
3. **金额精确比较**：三层金额均为 `DECIMAL` 精确运算，快照列 2 位小数，直接等值比较；不做浮点容差。
4. **窗口函数日期范围**：调用方保证 `@date_from <= @date_to`；非法范围返回空结果集，由页面/测试先行校验。
5. **操作人可信度**：会话上下文由应用设置，数据库无法证明「真的是该员工本人操作」；能证明的是
   应用声称的员工编号与实际 SQL 登录，两者都落库。更强的信任边界（过程内传参/行级安全）属 R07/S03。
