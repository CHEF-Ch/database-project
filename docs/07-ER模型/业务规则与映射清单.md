# 第五周：业务规则与映射清单

> 组内一份。以第一阶段 v0.1 的 17 张表为底稿，逐项写明：联系两端的最小/最大基数（参与约束）、适用条件、对应表与外码，以及当前由**约束 / 代码 / 人工检查**实现的规则。
> **本周只做分析与清单，不动表结构**（结构调整在第六周经 `migration.sql` 实施）。
> 事实来源：实体/属性/标识/联系/基数以 `docs/02` §2、§3、§5.2 为准；业务规则以 `docs/01` §4 为准；约束落地以 `sql/constraint.sql` 为准。本文只补两列——**参与约束（min..max）**与**实现方式**，不重写已有底稿。

## 0. 口径与读法

- **参与约束记法 `min..max`**：`min=1` 强制参与（必须关联到另一实体），`min=0` 可选参与（可为空 / 可不关联）。`max=1`、`max=N` 分别表示至多一、至多（可）多。
- **基数由业务规则定，不由样例定**：样例 7 张订单"每单都有明细"不构成"订单必有明细"的数据库约束；非会员单、平台单 `member_id = NULL` 是业务规则，不看样例取值。
- **实现方式三档**：
  - **约束**：由 `constraint.sql` 的 PK / UQ（含筛选唯一索引）/ FK / CHECK / NOT NULL / DEFAULT / 级联删除落地。
  - **代码**：应用层逻辑（第 7—9 周开发）、事务或触发器保证。
  - **人工**：流程约定、录入纪律，无任何技术手段兜底。
- 外码只保证"被引用的对象存在"，**不保证反向参与约束**（如"每单至少一条明细"），二者必须分开写。

## 2. 联系与映射清单（核心）

> 读法：`A min..max ──联系── B min..max` 表示"每个 A 关联 min..max 个 B，每个 B 关联 min..max 个 A"。共 20 条联系，覆盖全部 25 条外码。

### 商品域

| # | 联系 | 两端基数（min..max） | 适用条件 / 说明 | 对应表 · 外码 | 实现方式 |
| --- | --- | --- | --- | --- | --- |
| R1 | 商品 ─配方─ 原料 | 商品 **1..N** ─ 原料 **0..N** | 配方 = 商品×原料的标准用量；关系属性 `qty` | `item_recipe` · `FK_item_recipe_item_product` / `FK_item_recipe_item_material` | 引用存在 → FK；"每商品必有配方"→ **人工/代码**（无约束，结构上允许 0 行） |

## 4. 业务规则实现方式对照（约束 / 代码 / 人工）

> 对应作业要求"当前由约束、代码或人工检查实现的规则"。逐条对齐 `docs/01` §4 与 `constraint.sql`。

### 4.1 由数据库约束实现（`constraint.sql` 已落地，共 219 项中的键与 CHECK）

| 规则 | 约束 |
| --- | --- |
| 主码唯一 | 17 条 PK（含 5 处复合主码：配方/加料选项/订单明细/加料明细/补货明细） |
| 候选码唯一 | 3 条 `UNIQUE`（商品 `(name,size)`、原料 `name`、平台单号）+ 3 条筛选唯一索引（会员 `phone`、订单 `pay_txn_no`、储值流水 `external_ref`，均 `WHERE 列 IS NOT NULL`） |
| 外码引用存在 | 25 条 FK；其中 3 条 `ON DELETE CASCADE`（明细随订单、加料明细随明细、平台信息随订单） |
| 强制非空 | 各外码列及经办列（`employee_id`）NOT NULL |
| 枚举取值 | 22 条 `CHECK ... IN (...)`（渠道/状态机 6 态/糖冰温度/职务/原料类别/单位/流水类型/券状态等） |
| 取值范围 | `>= 0`：现存量/预留量/安全库存/积分/余额/实付/配送费；`> 0`：用量/杯数/单价/积分额/余额额/券门槛/券面额/保质期天数 |
| 跨列约束 | `reserved_qty <= stock_qty`；补货 `received_at ⟺ RECEIVED`；积分流水 `order_id ⟺ 非充值`；券 `discount <= threshold` 且 `valid_to >= valid_from` |
| 默认值 | 16 条 DEFAULT（售出状态、库存三量、券折扣 0、券状态等） |

### 4.2 由代码/事务实现（`constraint.sql` 明写"CHECK 表达不了"或属应用逻辑）

| 规则 | 为什么必须代码 | 依据 |
| --- | --- | --- |
| `item_addon_option.material_id` 须为 `ADDON` | 跨表读 `item_material.material_kind`，CHECK 表达不了（需触发器或标量 UDF） | `constraint.sql` 尾部"故意没写"第 2 项 |
| 预占 / 确认 / 释放三动作 + 幂等 | 涉及 `reserved_qty`/`stock_qty` 增减 + 写流水，须事务保证原子性与幂等（以订单号 + 支付流水号做唯一标识） | `docs/01` §3 主流程一、异常流程 |
| 积分计算（满 1 元记 1 分、按实付、余额支付不计分、平台单不计分、取整、退款冲正） | 业务计算逻辑，无落点可写成 CHECK | `docs/01` §4.1 |

| 缺货 / 会员余额不足拦截 | 需读快照动态判断可售量、余额 | `docs/01` 异常流程表 |
| 状态机流转（平台单无 PENDING、CANCELLED 仅来自 PENDING） | 状态转移合法性，CHECK 只能约束单列取值 | `docs/01` §4.6 |
| 临期推算（入库时间 + 保质期天数） | 查询侧计算，不存真实到期日 | `docs/01` §4.7 |

## 5. 候选改进项（供第六周 `migration.sql` 评估，非本周动作）

> 本节是"实现方式"里暴露出的、**当前靠人工兜、但其实可被约束表达**的点，记入 `v0.1-问题清单.md` 的候选素材，不在本周改库。

1. **`CK_shop_order_platform`**：`channel='PLATFORM' → order_mode IS NULL`（同表跨列，CHECK 可表达；`constraint.sql` 尾部将其误归为"需跨表读取"）。
2. **`CK_shop_order_pending`**：`order_status='PENDING' → pay_method IS NULL`（同表可表达）。
3. **`CK_inv_stock_log_order`** / **`CK_inv_stock_log_restock`**：`order_id ⟺ log_type='SALE'`、`restock_id ⟺ log_type='IN'`——与 `CK_member_point_log_order`（已写）同构，库存流水却未写。
4. **`CK_member_balance_log_order`**：`order_id ⟺ balance_type IN ('SPEND','REFUND')`——与积分流水同构，储值流水未写（R16/R18 不对称）。
5. **`CK_mkt_member_coupon_used`**：`used_order_id` 非空 ⟺ `coupon_status IN ('LOCKED','USED','RETURNED')`。
6. **"每单最多核销一张券"**：`mkt_member_coupon` 上对 `used_order_id` 加筛选唯一索引（`WHERE used_order_id IS NOT NULL`），可把"每单一张"从代码约束提升为结构约束。
7. **`item_addon_option` 的加料须为 `ADDON`**：需触发器或标量 UDF（跨表），是否值得在 v2.0（第 10—13 周触发器/存储过程阶段）落地，另行评估。

> 凡未列入 `constraint.sql` 却属"显然该有"的约束（如 `unit_price > 0`、`commission_amount >= 0`），遵循"先回填 `docs/02` 再改脚本"的既有口径，一并留第六周处理。
