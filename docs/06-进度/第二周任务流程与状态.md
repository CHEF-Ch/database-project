## 六、步骤 ① 设计约定（初步）：现在可确认的内容

### 1. 编号类字段

| 编号 | 类型 / 长度 | 格式 | 说明 |
| --- | --- | --- | --- |
| 门店订单号 | `CHAR(12)` | `YYYYMMDD` + 4 位当日序号（`202609160001`） | 含日期，序号跨天归零（**"统一连续"指各渠道共用一个序列，不是全局累加**）；一次填满 12 位，无尾随空格 |
| 平台订单号 | `VARCHAR(50)` | 外部平台给定 | **外部生成、长度不可控，必须变长**；唯一（候选码），非主码 |
| 商品编号 | `CHAR(8)` | `P` + 7 位序号（`P0000001`） | 类别字母前缀便于识别 |
| 原料/加料编号 | `CHAR(8)` | `M` + 7 位序号（`M0000001`） | 原料与加料共用一张表（`kind` 区分），故共用前缀 |
| 会员编号 | `CHAR(8)` | `C` + 7 位序号（`C0000001`） | |
| 员工编号 | `CHAR(8)` | `E` + 7 位序号（`E0000001`） | |
| 补货单编号 | `CHAR(8)` | `R` + 7 位序号（`R0000001`） | 单据，有业务身份 |
| 券规则编号 | `CHAR(8)` | `CP` + 6 位序号（`CP000001`） | 配置，`CP` 避开会员 `C` |

> 编号前缀已回填：补货单 `R`、券规则 `CP`（避开会员 `C`）；库存/积分/储值流水、会员持券用 `BIGINT IDENTITY` 代理键，无业务前缀（见 `docs/02` §5.1）。

### 2. 数值精度

| 用途 | 类型 | 理由 |
| --- | --- | --- |
| 金额（售价、加料单价、实付、券优惠、抽成额、余额、流水金额） | `DECIMAL(10,2)` | 人民币到分；**禁用 `FLOAT`/`REAL`**（浮点会致 `19.99−0.01 ≠ 19.98`） |
| 用量 / 库存量 / 安全库存 / 预留量 | `DECIMAL(10,2)` | 单位取**克 / 毫升**，用量几乎都是整数，无累计误差；留 2 位防"半勺" |
| 单位（克/毫升） | 单独一列 `unit`，**只在原料表存** | 配方与加料明细的用量单位**继承自原料**，不重复存（否则会出现"原料是克、配方写千克"的矛盾） |
| 抽成比例 | `DECIMAL(5,4)` 存小数（`0.2000`） | 计算式 `商品金额 * 比例` 一行写完，**不会漏掉 `/100`** |
| 加料数量 | `INT` | 份数，整数 |

**为什么"单位只在原料表存"要作为一条约定单列**：单位（克/毫升）是**原料自身的属性**，配方用量与加料用量都是在"用掉多少该原料"，单位天然跟随原料。若允许配方表再存一列 `unit`，就产生**同一份用量有两处单位记载**，两处可以互相矛盾（原料写"克"、配方写"千克"，数值 50 的含义差了 1000 倍，且没有任何约束能发现）。只存一处则矛盾在结构上不可能出现——这是**用表结构消灭一类错误**，而不是靠人工核对。第 4 周写 `CHECK` 时也无须为"单位一致性"造约束。

### 3. 时间类型

| 用途 | 类型 | 说明 |
| --- | --- | --- |
| 业务时间（下单、支付、出餐、入库、流水） | `DATETIME2(0)` | 秒级。`DATETIME2` 无 `DATETIME` 的 3.33ms 舍入（`23:59:59.997` 会跳到次日，做按天统计时会把零点的单算到邻天） |
| 纯日期（营业日、统计口径） | `DATE` | 不存 `DATETIME`，避免"`2026-09-16 00:00:00`"这种伪时间 |
| 取当前时间 | 用 `SYSDATETIME()`，**不用 `GETDATE()`** | `GETDATE()` 返回 `DATETIME` 类型，与 `DATETIME2` 列不配套 |

### 4. 命名风格

| 项 | 约定 |
| --- | --- |
| 保留字规避 | **`ORDER` / `USER` / `GROUP` / `KEY` / `DESC` / `STATUS` 等为 T-SQL 保留字**，订单表命名 `shop_order` 而非 `order`（`SELECT * FROM order` 会直接语法错误） |
| 大小写与分词 | 表名、字段名**全小写 + 下划线分词**（`order_item`、`unit_price`） |

### 6. 枚举与布尔字段的表示法 ★影响第 4 周全部 `CHECK`

**统一用英文大写码 + `VARCHAR(20)`**（短码用 `VARCHAR(10)`）。

**已定的只是"表示法"**：不采用单字母码（`'P'` 需额外解释）、不采用数字码（`WHERE status=3` 不可读，且须额外维护码表）。理由：① 第 4 周 `CHECK (order_status IN ('PENDING',...))` 一眼看懂，答辩可直接讲；② 样例数据自解释；③ `docs/01` 用的就是英文码，文档与表一致，无需翻译。

**布尔类字段不用 `BIT`，同样用枚举。** 理由：`docs/01` 中的"上下架""在职"都是**业务状态**，将来可能不止两个值（商品还有"售罄"/"停售"，员工还有"休假"）。`BIT` 只有两值余地，加第三态要改类型，而**改类型要动所有已录入数据**；枚举起步是加法。判据：**问"这个字段现在两个值，将来会不会需要第三个"**——会就用枚举，不会（如"是否删除"这类技术标志）才用 `BIT`。

> **各枚举的具体取值清单已回填**，见 [`docs/02-数据字典.md`](02-数据字典.md) §1.1——已逐项对齐 17 张表的实际字段（含布尔类字段的取值名）。

### 7. 文本字段的 `NVARCHAR` / `VARCHAR` 选择原则

**可能存中文的一律 `NVARCHAR`**（名称、地址、备注）；纯英文数字的用 `VARCHAR`（编号、邮箱、手机号）。

理由：`VARCHAR` 存中文受排序规则影响，某些设置下会乱码；`NVARCHAR` 是 Unicode，必定不乱码。

> **各用途的具体长度档位（名称类 100 / 地址 200 / 备注 500 等）待 ③ 定**，因为要看到实际字段才能判断是否够用。

### 8. 库存与数量类的"能否为 0"判别原则

| 字段（已见） | 能否为 0 | 说明 |
| --- | --- | --- |
| 现存量 `stock_qty` | 能（`>= 0`） | 0 = 卖完了，是有意义的状态 |
| 预留量 `reserved_qty` | 能（`>= 0`） | 0 = 无待处理预占 |
| 安全库存 `safety_stock` | 能（`>= 0`） | 0 = 该原料不设补货线 |
| 保质期天数 `shelf_life_days` | 不允许（`> 0`） | "能放 0 天"无意义 |
| 单位用量（配方、加料） | **不能**（`> 0`） | 见下 |
| 加料数量 | **不能**（`> 0`） | 见下 |

**判别方法（本条是原则，具体字段到 ③ 逐个套用）**：

> 问"**这一行存在，是为了记录发生了某件事吗？**"
> 是（**事件型**，如配方行、加料明细行）→ 数量必须 `> 0`；
> 不是（**状态型**快照，如库存量）→ 可以为 0。

**为什么事件型不能为 0**：用量 0 / 数量 0 表示"发生了 0 次"，语义自相矛盾——那一行就不该存在。若允许 0：用量 0 会让"写了配方却永不扣料"，库存账悄悄对不上；加料数量 0 会在统计中虚增"加料被点次数"（`COUNT(*)` 会计入它），且该行在金额与库存上完全隐形。

**另记（属第 4 周）**：`预留量 <= 现存量` 属**行级跨列约束**，不是列级约束，第 4 周用 `CHECK (reserved_qty <= stock_qty)` 表达。此处仅记录"这是一条约束"，不写 SQL。
