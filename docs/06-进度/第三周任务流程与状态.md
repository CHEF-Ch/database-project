# 第三周任务流程与状态

> 目标：按 `docs/02` 的数据字典**从空库**建出可运行的数据库，装载样例数据，完成增删改查，并保证脚本可复现。
> **本周第一次真的跑 SQL**——前两周的产出全是判断，本周开始有客观反馈（类型不符、外码不存在、约束被违反都会当场报错）。

**执行顺序按依赖排**：建表顺序由外码依赖决定（先建被引用的表），装载必须在建表之后，CRUD 必须在有数据之后。顺序错了不是"返工"，是**根本跑不起来**。

> **阶段参照（避免"阶段 N"歧义）**：阶段一（1—4 周，v0.1）／阶段二（5—9 周，v1.0）／阶段三（10—13 周，v2.0）／阶段四（14—17 周，v3.0）。**本周属阶段一**。凡文档写"留到阶段 N"而未注明周次的，先按此表换算，不要拿"当前周"去套。出处：`第一周任务讲解.docx` 四阶段总览表。

## 二、建表顺序（外码拓扑序）

> 课程提示第 1 条："先创建被外码引用的表，再创建引用它的表；删除时通常按相反顺序处理。"
> 本表由 `docs/02` §3.1 的 **25 条**关联推出——**没有任何一张表被它后面才出现的表引用**。
> （原写"24 条"，与 §3.1 实际的 #1—#25 行数不符，已按实际改为 25。`01-schema.sql` 实测建成 **25 条外码**，与 §3.1 一致——这条数字被 SQL Server 本身核对过了。）

| 批次 | 表 | 被谁引用 | 说明 |
| --- | --- | --- | --- |
| 1 | `item_product`、`item_material`、`member_member`、`staff_employee` | 被多表引用 | **无外码**，四张主数据表，可任意顺序 |
| 2 | `item_recipe`、`item_addon_option` | — | 只引用第 1 批（商品 × 原料） |
| 3 | `shop_order` | 被 order_item / order_platform / 各流水引用 | 引用第 1 批（会员、员工） |
| 4 | `order_item` | 被 order_item_addon 引用 | 引用 shop_order、item_product |
| 5 | `inv_restock` | 被 inv_restock_item、inv_stock_log 引用 | 引用 staff_employee |

**删除时按相反顺序**（10 → 1）。课程提示里"删除时通常按相反顺序处理"指的就是这个。

## 三、本周约束（不可突破）

1. **建表脚本必须能从头跑通**：不是"把文档翻译成 SQL"就算完——要在空库实测，报错就改。
2. **`01-schema.sql` 与 `docs/02` §2.2 必须一致**：字段名、类型、可空、默认值逐项对齐。若有差异，**要么改脚本、要么改文档**，不能两个版本并存。
3. **`docs/02` 第 2 周的约定不得在本周擅自变更**：类型、精度、可空性、枚举取值都已定稿（见第二周流程表 §四/§五）。本周若发现某个约定在 T-SQL 里写不出来（如 `CHECK` 无法表达、`CHAR` 长度不够），**记录下来并回填第二周文档**，而不是就地改掉。

## 五、对外码顺排的一个已知代价

`sql/02-seed.sql` 现有样例按业务故事组织（7 张订单，覆盖到店现金/余额/线上、平台、待支付、整单退款两类）。**但 `INSERT` 必须按外码顺序写**（先主数据、再订单、再明细），否则外码约束当场报错。

两者不矛盾：**脚本里的语句顺序按依赖排，注释里保留业务故事线**。第 4 步装载时按这个方式重排，故事线不要丢——它是第 ⑤ 步 CRUD 和第 4 周查询用例的数据基础。

## 六、实测暴露的 5 处缺陷（①②④ 跑通后回填）

> 本节是 §三 第 1 条"要在空库实测，报错就改"的**产出本身**：下面每一条都不是读文档读出来的，是 SQL Server 当场报错报出来的。
> 全部修正都按 §三 第 3 条"记录并回填第二周文档"执行——**改的是 `docs/02` + 脚本两边，不留两个版本**（§三 第 2 条）。

| # | 报错 / 现象 | 根因 | 落在 | 记录处 |
| --- | --- | --- | --- | --- |
| 1 | `String or binary data would be truncated`（`mkt_coupon_rule.coupon_type`） | `docs/02` 把该列定为 `VARCHAR(10)`，却给它登记取值 `FULL_REDUCTION`（14 字符）——**类型和自己的取值打架**。`item_addon_option.addon_status` 同病（`UNAVAILABLE` 11 字符，seed 未触发，属潜伏） | 两列放宽为 `VARCHAR(20)` | `docs/02` §5.7 #3、§1.1 #3/#17、§2.2-4/15 |
| 2 | `Violation of UNIQUE KEY constraint 'UQ_shop_order_pay_txn_no'. | 4 | `Invalid object name 'staff_employee'` | `02-seed.sql` **缺 `USE [MilkTeaShop]`**。每个脚本是独立一次 sqlcmd 进程，上下文不继承，按 `sql/README.md` 的命令（不带 `-d`）执行就停在 `master` | 补 `USE [MilkTeaShop];` | `docs/02` §5.7 #4 |
| 5 | `Cannot insert the value NULL into column 'employee_id'` | `02-seed.sql` 写于第二周 ④⑤，而 §5.7 #1 的**复核结论（改为非空）出现在其后**，seed 没跟着更新——**复核结论与产出脱节** | 三张自助单按 #1 的注记收银员 `E0000001` | `docs/02` §5.7 #5 |

**外加 1 处流程缺口**：缺陷 2/3/4 都属于"**照 `sql/README.md` 的命令跑不起来**"，而 README 的那串命令此前从未被真正执行过。说明 README 的执行顺序**必须由执行者逐条验一遍**，不能只当作说明文字写下来。

## 七、本轮实测结果（①—④ 段）

均用 `sql/README.md` 的命令原样执行（`-b -f 65001`，**不带 `-d`**）：

| 验证项 | 结果 |
| --- | --- |
| `00-create.sql` → `01-schema.sql` → `02-seed.sql` | 三个脚本 `exit=0` |
| 建表汇总 | 17 张表、25 条外码、36 条 CHECK、16 条 DEFAULT、17 个主码、6 个候选码 |
| 样例数据行数 | 17 张表全部有数据（7 张订单、12 条明细、36 条库存流水、3 位会员…），与 `docs/02` §4 的 7 张订单故事线一致 |
| 空库自检（负向） | 在非空库重跑 `01-schema.sql`，被拦住并提示"请先重跑 `00-create.sql`"，`exit=1` |
| 系统库安全闸（负向） | 把 `00-create.sql` 的库名误改为 `master` 后执行，`THROW 51001` 中止、`exit=1`，四个系统库完好 |
| **复现验证** | 完整跑两遍（每遍都从删库开始）：结构指纹 **210 条**（110 列 + 20 键 + 3 筛选索引含过滤条件 + 25 外码 + 36 CHECK + 16 DEFAULT；17 张表列数总和正好 110）、数据指纹 **68 行**；两遍 SHA256 **完全相同** |

> ⚠️ **一个教训（已踩过）**：用"把元数据导出成文本再比哈希"做复现验证时，必须**先断言那个文件里没有 `Msg ` 报错行**。第一版指纹 SQL 因排序规则冲突（`Latin1_General_CI_AS_KS_WS` vs `Chinese_PRC_CI_AS`，`+` 拼接目录视图列触发）整份文件只有一行报错——两遍当然"哈希相同"，结论却是假的，等于白得一个通过。修正办法是给目录视图的字符串列加 `COLLATE DATABASE_DEFAULT`。**"两次一致"只有在确认比的是真数据时才有意义。**
