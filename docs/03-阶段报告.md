## 2. 设计思路

### 2.1 经营场景与数据边界

- **场景**：校园周边奶茶店（单门店、单币种人民币），覆盖到店点单与外卖平台订单，提供会员积分/优惠券/储值、原料级库存与加料定制。
- **进库**（14 类）：商品、原料、配方、加料、订单、订单明细、订单加料明细、会员、积分/储值流水、优惠券、员工、补货单、库存流水、平台订单信息。
- **不进库/暂不进库**（10 类）：骑手信息与配送轨迹、第三方平台内部数据、支付密码/密钥、身份证等敏感资料、浏览轨迹、供应商合同/工资、多门店调拨、平台券成本分摊、原料批次级明细、真实顾客资料（样例全虚构）。

> 边界判据：是否被多个流程共享？未来要不要查询/统计/留痕/预测？是否随时间变化需留历史？——满足才进库，否则控制复杂度。

### 2.2 核心设计取舍（每个"为什么"）

| 取舍 | 选择 | 为什么 |
| --- | --- | --- |
| 商品 vs 原料分离 | `item_product` 与 `item_material` 分表，靠 `item_recipe` 配方关联 | 库存是**原料级**的：卖一杯按"配方 + 加料"扣原料，而不是卖一杯扣一杯成品；同一原料可同时是某商品的默认料、又是其它商品的加料 |
| 默认小料 vs 加料 | 配方内小料算商品价、不另收费；额外加料另计费且另扣料 | 避免重复收费/重复扣料，是加料费规则的核心 |
| 订单明细存快照 | 明细记成交价快照，不随商品调价变化 | 历史订单必须可追溯原价，商品改价不影响已成交订单 |
| 会员存余额快照 | `member_member.balance` 存当前值 + 流水表 | 存快照的唯一硬收益是能写 `CHECK (balance >= 0)`，纯流水只能事后 `SUM` 发现、拦不住透支 |
| 流水 vs 汇总 | 积分/余额/库存均留流水表 | 解释"为什么是这个数"，可审计、可冲正 |
| 平台单 vs 到店单 | 共用同一状态机，三处差异 | 平台单由平台预收款（无 PENDING、不设预占）、交餐给骑手即"完成"；到店单有预占/确认/释放三动作 |
| 临期预警 | 原料表存保质期天数 + 视图推算，不记批次到期日 | 阶段一不建批次级模型（FIFO/跨批扣料），临期只提醒不拦截 |

### 2.3 主码 / 候选码 / 外码的设置与理由

- **主码（17）**：业务编号统一连续（`P0000001` / `M0000001` / `C0000001` …），跨来源统一编号，如门店订单号到店单与平台单共用。
- **候选码（6）**：3 条用 `UNIQUE` 约束（如原料名、商品名+杯型、平台订单号），3 条用**带筛选的唯一索引**——因为 `member_member.phone`、`shop_order.pay_txn_no`、`member_balance_log.external_ref` 允许多个 NULL，而 SQL Server 的 `UNIQUE` 约束只允许一个 NULL，与"可空、多 NULL 不冲突"冲突，故用 `CREATE UNIQUE INDEX ... WHERE col IS NOT NULL`。
- **外码（25）**：订单明细→订单、配方→商品+原料、加料明细→订单明细等；其中 3 条（订单明细/加料明细/平台单信息）带 `ON DELETE CASCADE`。
- **约束显式命名**：所有 PK/FK/CK/DF 都显式命名（`PK_表名` / `FK_子表_父表` / `CK_表名_字段名` / `DF_表名_字段名`），因为不命名时 SQL Server 会给 CHECK/DEFAULT 起带随机十六进制后缀的名字，两次复现的约束名就不一致，"得到相同的表结构"这条复现要求当场不成立。

### 2.4 角色与权限划分（正反例）

按第一周 8 角色清单，落在数据库的是 4 个业务角色（非会员顾客、外卖平台、DBA 不在此列）：

| 角色 | 最小权限 |
| --- | --- |
| 收银员 `role_cashier` | 读商品/配方/加料/会员/券；下单写订单三表；**不可**改库存、券规则、会员余额 |
| 制作员 `role_maker` | 读订单/配方；仅可改 `shop_order.order_status` 一列；**不可**读会员余额/地址 |
| 库存管理员 `role_stock_keeper` | 管库存/补货/流水；**不可**访问会员资金、不改成交价 |
| 店长 `role_manager` | 维护商品/配方/加料/券规则、审核退款/报损；业务管理 ≠ DBA，**无** DDL/GRANT 权限 |

> 权限遵循**最小权限**原则：只 GRANT 需要的、不 DENY，"越权"= 根本没授权，操作自然被拒（SELECT/写越权报 229，DDL 越权报 262）。

## 3. 实验步骤

1. **建库**（`00-create.sql`）：先 `DROP` 同名库再 `CREATE`（`Chinese_PRC_CI_AS`），使每次复现都从空库出发；`DROP` 前 `SET SINGLE_USER WITH ROLLBACK IMMEDIATE` 断开占用连接。

4. **样例数据**（`02-seed.sql`）：按外码顺序 INSERT，7 张订单覆盖全部状态与支付组合。
5. **视图**（`view.sql`）：`CREATE OR ALTER VIEW` 建 4 个统计视图。

## 5. 完整性能力与限制

| 规则 | 当前保证方式 |
| --- | --- |
| 主码 / 候选码唯一 | 数据库强制（PRIMARY KEY / UNIQUE / 筛选唯一索引） |
| 外码引用完整性 | 数据库强制（FOREIGN KEY，3 条带 ON DELETE CASCADE） |
| 枚举取值（杯型/订单状态/职务/流水类型等） | 数据库强制（CHECK） |
| 数值非负（库存量、金额、积分、余额、抽成比例等） | 数据库强制（CHECK） |
| 预留量 ≤ 现存量 | 数据库强制（跨列 CHECK `CK_item_material_reserved_le_stock`） |
| 会员余额非负 | 数据库强制（CHECK `balance >= 0`，依赖余额快照） |
| 券有效期止早于起 / 满减券边界 | 数据库强制（CHECK） |
| 状态与字段一致性（如 RECEIVED 必填 received_at） | 数据库强制（跨列 CHECK） |
| 预占 / 确认 / 释放三动作及幂等 | 靠脚本/事务保证（阶段一演示事务回滚，触发器/存储过程留第三阶段） |
| 积分"支付成功才记"、券锁定/核销流转 | 靠脚本/事务保证（无完整支付闭环，阶段一用演示数据） |
| 原料批次级效期 / 逐批成本 / FIFO 扣料 | 未做（临期仅"提醒性质"，批次级模型留阶段二评估） |
| 会员逐人数据隔离 | 未做（阶段一为员工角色级授权，应用身份映射留后续阶段） |

## 6. 实验总结与答辩准备

### 6.1 踩过的坑、改过的点

1. **sqlcmd 默认 `QUOTED_IDENTIFIER = OFF`**：带筛选唯一索引的三张表（`shop_order`/`member_member`/`member_balance_log`）在 SSMS 里能建、按 README 的 sqlcmd 命令却报 `Msg 1934`——根因是 SSMS 默认 `QUOTED_IDENTIFIER = ON`、sqlcmd 默认 OFF。最终在每个脚本开头显式写死 `SET QUOTED_IDENTIFIER ON; SET ANSI_NULLS ON;`。
2. **`UNIQUE` 约束只允许一个 NULL**：与 `docs/02` §5.2"可空、多 NULL 不冲突"冲突，改用筛选唯一索引解决。
3. **约束不显式命名会导致复现指纹不一致**：SQL Server 自动命名的 CHECK/DEFAULT 带随机十六进制后缀，两次复现名字不同。改为显式命名（`CK_表名_字段名` 等），保证复现"得到相同的表结构"。
4. **列级 vs 跨列 CHECK 的取舍**：原以为"跨列 CHECK 留第 4 周"，查证后推翻——第三周任务 §2 明写要"设置检查约束"且未区分列级/跨列，故 constraint.sql 统一写齐。
5. **seed 补低库存原料**：库存预警查询（Query 04）此前无结果，补 `M0000008 红豆`（现 600 < 安全 1000）后才有非空输出。

### 6.2 答辩可能被问的问题

- **为什么商品和原料要分两张表？** 因为库存是原料级的，卖一杯按配方+加料扣原料；同一原料可同时是某商品的默认料和另一商品的加料。
- **为什么候选码用筛选唯一索引而不是 UNIQUE 约束？** UNIQUE 只允许一个 NULL，与"可空、多 NULL 不冲突"矛盾。
- **为什么会员要存余额快照？** 纯流水只能事后 SUM、拦不住透支，存快照才能写 `CHECK(balance>=0)`。
- **平台单为什么没有 PENDING 状态？** 平台已预收款，门店收到即 PAID 起步、接单即确认耗用，不设预占。
- **为什么约束要显式命名？** 不命名会带随机后缀，两次复现的约束名不一致，破坏"复现得到相同表结构"。
- **角色权限怎么证明"越权被拒"？** 最小权限 = 只 GRANT 需要的不 DENY，越权操作自然报 229/262；role.sql 用 `EXECUTE AS USER` 切身份 + 事务回滚做了 13 条正反例。
- **INNER JOIN 和 LEFT JOIN 你怎么选？** 会员消费汇总用 `LEFT JOIN`（保留无订单会员），销量统计用 `INNER JOIN`（只要成交明细）。

## 3. 第六周：范式化与结构迁移

### 3.1 依赖与范式分析（②）

- 17 表 1NF / 2NF 全部满足；3NF / BCNF 16/17。唯一严格违例是 `shop_order.total_amount`（`{item_subtotal, coupon_discount} → total_amount` 经非主属性传递依赖）。

### 3.2 重构方案（③）

- 结论 **0 拆 0 并**：现有结构整体合理，`shop_order` 保留并补 P12 等式 CHECK（`total = subtotal − discount`）。
- 迁移内容 = **+1 列**（`order_item_addon.addon_price` 快照）+ **15 CHECK**（P1–P8、P12）+ **1 筛选唯一索引**（"每单最多核销一张券"，`WHERE used_order_id IS NOT NULL`）。
- 迁移前预检 15 项全 0，现有数据可直接加约束。

### 3.3 迁移与回归（④⑤）

- ④ 在副本 `MilkTeaShop_v01` 上执行 `migration.sql`，结构指纹 **219 → 236**，退出码 0。

### 5.2 分层结构与职责

| 层 | 目录 | 负责 | 不承担 |
| --- | --- | --- | --- |
| 页面层 | `app/pages/`、`app/templates/` | 接参、表单基础校验、渲染、302 重定向 | 不直连数据库、不拼 SQL、不决定数据库权限 |
| 业务层 | `app/services/` | 认证、权限矩阵、业务规则、事务边界、异常归类 | 不把原始数据库异常返回前端 |
| 数据访问层 | `app/dao/` | 参数化 SQL、连接 / 游标 / 事务 / 释放、结果映射 | 不接收模板逻辑、不拼接用户输入 |
| 数据库层 | `MilkTeaShop_v01` | 表、约束、视图、角色与权限 | 不依赖页面隐藏按钮保证安全 |

横切：`app/config.py`（唯一读环境变量的地方）、`app/errors.py`（错误码、请求标识 `rid`、全局异常处理与日志）、`app/csrf.py`（CSRF 令牌）、`app/services/permissions.py`（权限矩阵）。

### 5.3 两条调用链

```text
查询（GET /products/）：
  浏览器 → product 蓝图（role_required("product.read")）→ permissions 判定
        → dao.db_cursor() → 参数化 SELECT → SQL Server
        → 结果映射 → Jinja2 渲染 → 浏览器

修改（POST /orders/，下单）：
  浏览器提交 → 页面层接参与基础校验（杯数、糖冰温、会员号格式）
            → order_service.create_order（服务端重算金额、校验库存 / 加料归属 / 券门槛）

```

页面层不出现 SQL；全部用户输入经 pyodbc 参数绑定；金额、库存是否充足、券能否使用、状态能否跳转一律由业务层判定，客户端提交的金额字段被丢弃。

### 5.4 认证、角色与三层权限

- **账号与会话**：5 个配置内 demo 账号（店员 / 顾客 / 制作员 / 库存管理员 / 店长），代码只存密码哈希；登录成功后写入 session，角色与会员 / 员工绑定只从服务端 session 取，不接受前端传 `role`。
- **权限矩阵**：5 角色 × 11 权限点，唯一事实来源是 `app/services/permissions.py`；页面按钮按权限隐藏只是体验控制，路由用 `role_required` / `role_required_any` 后端再校验一次。
- **数据库层**：`sql/app_login.sql` 建 5 个业务 SQL 登录（`login_clerk / login_customer / login_maker / login_stock / login_manager`）+ 1 个写事务账户 `login_app → role_app`；新建 `role_customer`，补 `role_cashier.item_material`、`role_maker.item_addon_option` 的 SELECT，给 `role_manager` 补 `item_material` 的 SELECT（不再用 `VIEW DEFINITION` 掩盖缺口）。
- **列级收窄**：店员对 `shop_order` 由整表 UPDATE 收窄为 8 列（状态 / 支付 / 完成时间 / 三金额），退款额、会员、经办人、创建时间仅店长可写；制作员仅 `order_status`（+ `completed_at`）。实测店员写 `refund_amount` → 230，店长 → OK。
- **三层一致性**：`docs/09 §8` 矩阵、`permissions.py`、路由装饰器由 `permission_matrix_test.py` 静态逐格比对，未接线权限仅 `coupon.write`（券维护页留 v2.0）。
- **`trusted` 与 `sql` 的实质差别**：`trusted` 下所有连接都是当前 Windows 账户（sysadmin），数据库权限层不生效；权限正 / 反例证据一律在 `DB_AUTH=sql` 下生成。两份证据同时存在，不能拿 `trusted` 的运行结果证明受限账户有效。
- **行级隔离**：数据库层不区分行（实测 `login_customer` 能读全部 7 张订单），顾客“只看自己的单”靠应用层 `WHERE member_id = ?`；`member_id` 只从 session 取，顾客分支禁止透传请求参数。
- **为什么需要 `role_app`**：一笔订单要在一个事务里写 10 张表，而按最小权限切出的 5 个业务角色没有任何一个能覆盖这 10 张表。`role_app` 只用于订单 / 库存 / 流水 / 会员 / 券的写事务，无 DDL、无 GRANT、无 DELETE；代价是第 4 周的列级收窄对“经应用的订单写”不再生效，这条已在 `docs/09 §10` 写明。

### 5.5 订单事务与关键业务规则

- **同一事务边界**：订单头 + 明细 + 加料 + 库存预占 / 确认 / 扣减 + `SALE` 流水 + 券锁定 / 核销 / 退回 + 会员积分 / 余额快照与流水 + 平台订单信息，全部在 **同一个 `db_cursor("app", commit=True)`** 内；任一异常整体回滚，不留半条订单。
- **订单号**：应用层 `MAX(当日序号)+1`，同一事务内 `WITH (UPDLOCK, HOLDLOCK)` 取号，撞 `PK_shop_order` 最多尝试 3 次（1 次初始 + 2 次重试）；保留 `YYYYMMDD + 4 位当日序号`、跨天归零的口径。
- **库存四动作**：下单预占（只增 `reserved_qty`，不写流水）→ 支付确认（扣 `stock_qty` + 写 `SALE`）→ 取消释放 → **平台单直接扣减**（不预占，`deduct_available`，订单与 `SALE` 同一事务）；条件 UPDATE 防超卖，拒绝非正数量。
- **券**：现金单当场核销；挂单先锁定（带 `used_order_id`），支付转已用；取消 / 整单退款退回为 **未使用**（`UNUSED` 并清空 `used_order_id`），不是作废。
- **积分 / 余额**：现金 / 线上按实付计分，余额支付不计分；退款冲正积分、回补余额，**不回补库存**。
- **状态机**：`PENDING → PAID → MAKING → COMPLETED`，`PENDING` 仅可取消；已付款单走 `REFUNDED`；制作员只能 `PAID → MAKING → COMPLETED`。
- **金额与幂等**：服务端按主数据重算（忽略客户端金额）；同一 `pay_txn_no` 重复支付幂等返回，撞其它订单 409；重复退款 / 取消 / 验收均 409。

### 5.7 已知限制（v1.0 记录，v2.0 处理）

- **“必要的删除”采用“不物理删除”口径**：任务要求的删除能力在本项目中统一用**状态位 + 冲正**表达——商品下架（`sale_status=OFF_SHELF`）、
  订单取消/退款（`order_status=CANCELLED/REFUNDED`）、库存靠 `inv_stock_log` 的 `GAIN/SHORT/IN` 冲正、券靠 `coupon_status` 回转；
  全应用 0 处 `DELETE`。原因：25 条外码中有 3 条 `ON DELETE CASCADE`（删订单会静默带走明细），而删商品会被配方外码拦住；
  且库存/积分/余额流水是审计账、统计视图与 `regression.sql` 都按行存在计口径。若需真删，v2.0 加软删除列 + 归档页并同步刷新指纹。
  详见 `docs/09-应用开发/结构与运行.md` §10 首条。
- **CSRF：已接入自研同步令牌（2026-11-10）**：`app/csrf.py` + 10 个 POST 表单隐藏域 + 请求头 `X-CSRF-Token`；
  无令牌/错令牌一律 `E2003/403`（集成用例 ERR-11 断言），零新增依赖；原残留的 `GET /logout` 登出型 CSRF
  已于 2026-11-11 修复（改为 `POST /logout`，`GET` 现返回 405，AUTH-06 断言）。
- **会话无显式超时**：未设 `PERMANENT_SESSION_LIFETIME`，依赖“关浏览器失效 + `SECRET_KEY` 每进程随机（重启即全失效）”；

- **券审计**：退券清空 `used_order_id`，逐券使用史需 v2.0 的券使用流水表。
- **登录凭据**：配置内 demo 账号；`app_user` 表与 `DbUserStore` 切换留 v2.0。
- **其他**：`SEQUENCE` / 触发器、`total_amount` 计算列、`quote` 精确预览、P9 跨表加料约束均留 v2.0。
  **日志不轮转**（`FileHandler` 单文件追加，`logs/` 不入库）：课设量级（实跑一轮约 1.7 MB）足够，交付前手动清理一次即可；
  若需长期运行再加 `RotatingFileHandler(maxBytes=5MB, backupCount=3)`（注意保留 `_pi_app_file` 去重标记，并同步文档里的 `app.log.1…3`）。

### 5.8 亮点（可直接引用的 4 条）

1. **权限三层一致，且有分层证据**：页面按钮显隐、后端 `role_required`、数据库受限登录三层对同一张 5×11 矩阵负责；

   `shown <= total` 恒真式、用 `MAX(order_id)` 取错对象），逐条修掉而不是放过。
4. **`/health` 结构指纹探针**：把"应用连的是不是 v1.0 库"变成可机器判定的 `236 / match=true`，

## 6. 第二阶段实验总结

### 6.1 踩过的坑、改过的点

1. **迁移动的是副本**：`migration.sql` 只在 `MilkTeaShop_v01` 上执行，源库 `MilkTeaShop` 保持 v0.1；指纹 219 → 236 有备份与回归双重证据。
2. **`sqlcmd` 默认 `QUOTED_IDENTIFIER = OFF`**：带筛选唯一索引的三张表在 SSMS 能建、按 README 的 sqlcmd 命令报 `Msg 1934`；脚本开头显式 `SET` 写死。
3. **`2627` 被子串 `262` 误判为“无权限”**：错误分类改为按括号内消息号精确匹配，并先判约束类再判事务 / 权限类。
4. **`.env` 的 BOM**：Windows 记事本保存的 UTF-8 带 BOM，按 `utf-8` 读取首行键名会带上 `\ufeff`；改为 `utf-8-sig`。
5. **`VIEW DEFINITION` 掩盖授权缺口**：`/health` 曾报 216 而非 236，差额 20 正是 `item_material` 的全部结构贡献；真因是 `role_manager` 缺该表 SELECT。补 SELECT、撤销 `VIEW DEFINITION`，不用更高权限绕过去。
6. **脚本与库漂移**：`app_login.sql` 改了授权但没人重跑，`DB_AUTH=sql` 下顾客下单页 403；重跑脚本后恢复，并把“改授权脚本必须重跑”写进复核清单。
7. **`r.items` 撞 dict 方法名**：补货单验收页模板用点号访问 `items`，拿到的是 dict 方法而非明细；改为 `r['items']`。
8. **`SEQUENCE` 与“每日归零”冲突**：初版建议加 `SEQUENCE` 最干净，回查 `docs/02 §5.6` 后发现单号按日归零，改为应用层 `MAX+1` + 撞主码重试。

### 6.2 答辩准备

- **为什么分四层？** 页面层只接参与渲染，业务层管规则与事务，DAO 是唯一碰 SQL 的层，数据库层用角色与约束兜底；换数据库或换页面都不影响另外三层。
- **怎么保证“不会留下半条订单”？** 订单头 / 明细 / 加料 / 库存 / 流水 / 券 / 积分 / 余额 / 平台信息在同一 `db_cursor("app", commit=True)` 内，异常整体回滚；测试用“库存不足 → 409 且订单数 / 流水 / 预占全不变”验证。
- **权限怎么证明？** 三层：`docs/09 §8` 矩阵 → `permissions.py` + 路由装饰器（静态逐格比对）→ 数据库受限登录直连实测 17 项（229 / 230 / 262）。`trusted` 下权限层不生效，所以证据分两份。
- **为什么顾客能下单却改不了库存？** `role_customer` 对订单三表有表级 INSERT，对 `item_material` 只有列级 `UPDATE(reserved_qty)`；`stock_qty` 仍 230。
- **`role_app` 是不是权限失控？** 它是“跨 10 张表单事务”的必然结果；只授写事务所需对象、无 DDL / GRANT / DELETE，退款等业务判定仍在服务层与页面层。
- **测试做到什么程度？** 132 条用例按 ID 逐条断言，trusted 128 PASS / 0 FAIL / 4 SKIP（DB 层权限项在 sql 版执行），另有 7 个专项自检脚本与 4 路交叉复核记录。
