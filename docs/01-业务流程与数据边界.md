# 第一周：经营场景与业务需求

> 本周不写 SQL、不建表，重点是**定边界、定角色、定流程、定规则**。产出：业务流程、角色与职能清单、数据边界清单、业务规则清单。

## 1. 项目定位与边界

- **项目名称**：奶茶店经营管理系统（暂定名，可改）
- **一句话定位**：服务一家校园周边奶茶店，销售现制饮品，覆盖**到店点单**与**外卖平台订单**，并提供会员积分/优惠券/储值、原料级库存与加料定制。
- **场景**：奶茶店（单门店、单币种人民币）

**复杂度控制（明确"不做"什么，防止越做越大）**：

| 项 | 本版决定 |
| --- | --- |
| 销售渠道 | 到店（COUNTER：收银台代录 + 扫码小程序自助点单）+ 外卖平台（PLATFORM：美团/饿了么）；**不做自营商城**（小程序为到店自助点单、现场取餐，非送货商城） |
| 外卖范围 | 只做**平台侧**：记录平台订单号、平台抽成、配送地址与配送费；门店到"交餐给平台骑手"为止，**不管理骑手、不跟踪配送轨迹** |
| 定制粒度 | **重定制**：糖度 / 冰量 / 温度 + **加料**（珍珠/椰果/布丁等）；加料会按其用量**扣减对应原料库存** |
| 库存口径 | **原料级**：按"配方 + 加料"扣料，而非卖一杯扣一杯成品 |
| 会员 | 积分、优惠券、储值（余额）；积分/余额保留流水 |
| 退款 | 阶段一仅支持**整单退款**，不支持部分退款 |

## 2. 角色与职责

> 每个角色都写清「职责 + 权限边界」，权限边界直接为第 4 周 role.sql 铺路。

| 角色 | 职责 | 权限边界 |
| --- | --- | --- |
| 非会员顾客 | 到店点单（收银台代录 / 小程序游客）、付款、取餐，或通过外卖平台下单、查单 | 不享会员积分/券/储值；不注册个人身份，不直接访问数据库 |
| 会员 | 到店点单（收银台扫会员码 / 小程序登录）、积分、用券、储值、查自己订单；也可通过外卖平台下单（不关联会员权益） | 只能访问自己的资料与资产 |
| 收银员 | 收银台代录、关联会员、收款、核对取餐 | 不可改库存成本、券规则、会员余额 |
| 制作员 | 查看制作任务、按定制制作、反馈完成 | 只需饮品选项与加料，不需要会员余额/地址 |
| 库存管理员 | 原料入库、盘点、登记损耗、提补货需求 | 不访问会员资金，不改成交价 |
| 店长 | 维护商品/配方/加料/券规则，审核退款、报损 | 业务管理 ≠ 数据库管理员 |
| 外卖平台 | 作为**外部订单来源（渠道）**，下发平台订单 | 不是数据库登录角色，不入库授权 |
| 数据库管理员 | 建库、授权、备份、技术维护 | 技术角色，不作为日常收银账号 |

补充：一名员工可兼任收银与制作；成员分工 ≠ 经营角色。阶段一数据库演示**员工角色级授权**；会员的**逐人数据隔离**留到应用身份映射阶段，不直接开放数据库登录。

## 3. 业务流程

### 主流程一：到店点单

1. 顾客到店，两种下单方式：**扫码小程序自助**（顾客手机点单，登录即会员或游客）或**收银台代录**（收银员选饮品、杯型、糖度/冰量/温度、加料、数量）
2. 关联会员：小程序登录即会员；收银台可扫会员码（可选）→ 校验可用券/余额 → 计算应付（商品额 − 券优惠 + 加料费）
3. 核对原料可用量（现存量 − 预留量）→ 预留原料（含加料；同一原料不可重复分配给多笔待支付订单）
4. 顾客付款（现金 / 线上支付 / 会员余额）
5. 支付成功 → 预留转实际耗用、写库存流水、核销券、扣余额 → 订单进入制作队列（重复支付通知不重复扣料/扣余额/核销券）
6. 制作员按定制制作 → 出餐 → 顾客取餐
7. 完成后按实付累计积分

### 主流程二：外卖平台订单

1. 顾客在外卖平台（美团/饿了么）下单 → 平台向门店下发订单（平台订单号）
2. 门店收单 → 录为 PLATFORM 渠道订单，记配送地址与配送费
3. 校验/预留原料 → 制作时预留转实际耗用 → 制作员制作 → 打包交餐给平台骑手（门店职责到此为止）
4. 后续配送由平台负责，门店不跟踪；结算时按平台抽成对账

### 异常 / 配套流程

| 场景 | 处理流程与数据影响 |
| --- | --- |
| 原料不足 | 提示更换商品/加料，或拒绝下单；不产生超卖 |
| 未付款取消 / 超时 | 释放原料与券预留，不产生退款与积分 |
| 已付款取消 | 整单退款，退回余额/积分冲正；已耗用原料不自动恢复 |
| 会员余额不足 | 整单改用其他渠道，或先充值 |
| 券不符合条件 | 校验归属/有效期/门槛，不满足则不可用 |
| 加料缺货 | 该加料不可选，提示顾客 |
| 补货 / 盘点 | 入库记正向流水，损耗记负向，差异记录原因，不覆盖历史 |
| 平台订单取消/异常 | 按平台通知处理，保留平台订单号便于对账 |
| 平台单重复下发（幂等） | 同一平台订单号推两次时只录一笔，不重复扣料；平台订单号唯一防重 |
| 对账差异 | 平台结算抽成/金额与门店记录不符，按平台订单号核对并登记差异 |
| 支付回调超时 | 顾客已付款但门店未收到成功通知，人工核对后补录，避免漏单 |

## 4. 业务规则（本周定稿）

> 这些规则直接决定第 2 周表结构和第 3 周 SQL，本周定死，逐条经组内确认。

### 4.1 积分规则

- **每满 1 元记 1 分**，按订单**实付**计（已扣券优惠、已含加料费），不含配送费、不含充值。**仅对会员的到店单累计**；平台单不关联会员、非会员游客单均不计分。
- **取整**：不满 1 元的部分不计（实付 15.6 元 → 记 15 分），不产生小数分。
- **支付成功才记**；未付款、已取消、已退款的不记，退款时冲正已记积分并保留冲正流水。
- 第一阶段积分**只累积、不消耗**（积分兑换留待后续阶段）。

### 4.2 加料费

- **默认小料 ≠ 加料**：商品配方里**已含**的小料（如珍珠奶茶自带的珍珠）算在商品价内、扣料也在配方用量内，**不算加料、不额外收费**；"加料"特指在默认配方之外**额外添加**的小料。同一原料可既是某商品的默认配方料、又是其它商品的加料选项（珍珠 = 珍珠奶茶的默认料，也可作为四季春茶的加料）。
- **加料既扣料、也加钱**：每种加料有**独立单价**（如珍珠 +2 元、椰果 +1 元）。
- **金额影响**：订单应付 = 商品价 + Σ(加料单价 × 数量) − 券优惠 + 配送费（配送费仅平台单）。
- **库存影响**：加料按配方用量**扣对应原料**，与饮品主料同规则。
- **同款加料多份**：允许"珍珠 ×2"，费用与扣料均按数量累加。
- **缺货**：加料缺货时该加料不可选（见异常流程表）。

### 4.3 平台抽成

- **固定比例 20%**（样例值，可改），不做分档，作为字段存在。
- **记录口径**：平台订单信息里记平台名、平台订单号、**抽成比例**、**抽成额**。
- **抽成额** = 顾客实付 × 20%。
- **门店实收** = 顾客实付 − 抽成额（对账、算真实营业额用）。平台单不关联会员、不计积分（见 4.1）。

### 4.4 券规则

- **只做满减券**（满 X 元减 Y 元），不做折扣券、无门槛券、运费券。
- **门槛口径**：满减门槛按**券前金额**（商品 + 加料）算。
- **每单最多用一张券**，不可叠加。
- **校验点**：归属（谁的券）、有效期、是否已用、是否满足门槛。
- **状态流转**：未使用 → 已锁定（下单）→ 已核销（支付成功）/ 已退回（取消或整单退款）。
- **退款**：整单退款时券**退回**为未使用，而非作废。
- **优惠快照**：订单明细记录券前金额与券优惠快照，券规则后续变更不影响历史订单。

### 4.5 订单来源与订单号

- **渠道**（订单主表字段，枚举）：`COUNTER` 到店 / `PLATFORM` 平台，决定订单走哪套流程。
- **下单方式**（仅到店单，字段）：`收银台代录` / `扫码小程序自助`，决定谁录入、如何关联会员；平台单无此维度。
- **平台名**（平台订单信息子表字段）：仅当渠道 = PLATFORM 时存在，如 `美团` / `饿了么`；到店单**无此行**。
- **门店订单号**（订单主表主键）：门店**自己生成、所有来源统一连续编号**，到店单与平台单共用一个编号。
- **平台订单号**（平台订单信息子表字段）：外部平台（美团/饿了么）给的**外部单号**，仅平台单有，用于对账，**不是主键**。
- **差异字段归属**：平台订单号、抽成比例/额、配送地址、配送费只在渠道 = PLATFORM 时存在，挂平台订单信息子表；到店单不关联。

### 4.6 订单状态机

> 到店单与平台单**共用同一套状态机**，两处差异："完成"的定义（到店 = 顾客取餐，平台 = 交餐给骑手）与平台单无待支付阶段（见下）。

```
PENDING(待支付) → PAID(已支付) → MAKING(制作中) → COMPLETED(已完成)
                      ↓
                CANCELLED(已取消)
               PAID/COMPLETED → REFUNDED(已退款)
```

| 状态 | 含义 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| PENDING 待支付 | 已下单未付款 | 下单成功（预留原料/锁定券） | 付款成功 / 取消或超时 |
| PAID 已支付 | 已付款待制作 | 付款成功（扣料/核销券/计积分） | 进入制作队列 |
| MAKING 制作中 | 制作员接手制作 | 制作员接单 | 出餐完成 |
| COMPLETED 已完成 | 已出餐/交付 | 出餐完成 | 终态 |
| CANCELLED 已取消 | 未付款取消 | PENDING 时取消/超时 | 终态（释放预留，不计积分） |
| REFUNDED 已退款 | 已付款后退款 | PAID/COMPLETED 后整单退款 | 终态（退余额/退回券/冲正积分） |

- 平台单由平台**预收款**，门店收到即 `PAID` 起步，**无 `PENDING` 阶段**；`PENDING → CANCELLED`（未付款取消）仅对到店单。
- 退款只能从已支付态发起（`MAKING` 之后的退款仍按整单退款处理，已耗用原料不自动恢复）。
- `CANCELLED` / `REFUNDED` 为**终态**，不可再跳转。
- 状态机本周只做**业务定义**；用 `CHECK` 约束或状态字段落地留到第 3、4 周。

## 5. 数据边界：进库

> 判断标准：是否被多个流程共享？未来要不要查询/统计/留痕/预测？是否随时间变化需留历史？

| 数据 | 主要内容 | 原因 |
| --- | --- | --- |
| 商品 | 名称、杯型、售价、上下架状态 | 统一定价与点单 |
| 原料 | 名称、单位、现存量、预留量 | 原料级库存，支撑缺料判断 |
| 配方 | 商品—原料、每杯标准用量 | 一杯饮品耗用哪些原料 |
| 加料 | 珍珠/椰果等，及其单价、单位用量 | 定制扣料，加料本身也是原料 |
| 订单 | 渠道、下单方式、会员、金额组成、状态、时间 | 追踪完整交易 |
| 订单明细 | 商品/规格快照、数量、成交价、糖度/冰量/温度 | 历史订单不随商品调价变化 |
| 订单加料明细 | 每行明细的加料及用量 | 定制扣料与追溯 |
| 会员 | 编号、联系方式、积分、余额 | 关联订单与会员权益 |
| 积分/储值流水 | 变动类型、金额、关联订单 | 解释"为什么是这个数" |
| 优惠券 | 规则、有效期、会员领券与使用状态 | 防重复使用/用他人券 |
| 员工 | 编号、姓名、职务、在职状态 | 经办与权限依据 |
| 库存流水 | 出入库类型、数量、经办 | 库存可追溯 |
| 平台订单信息 | 平台名、平台订单号、抽成、配送地址/费 | 平台对账与结算 |

## 6. 数据边界：不进库 / 暂不进入

| 数据 | 决定 | 原因 |
| --- | --- | --- |
| 骑手信息、配送轨迹、地图路线 | 不进入 | 配送归平台，门店不管理 |
| 第三方平台内部数据 | 暂不进入 | 只存平台订单号/抽成用于对账 |
| 支付密码、银行卡、平台密钥 | 不作为业务数据存储 | 由支付服务处理，密钥不进 Git |
| 身份证、生日、健康资料 | 不收集 | 完成购买不需要 |
| 浏览轨迹、广告画像、聊天录音 | 不进入 | 本版聚焦交易 |
| 供应商合同、工资、水电、税务 | 暂不进入 | 不建完整财务/人事系统 |
| 多门店调拨、自动采购预测 | 暂不进入 | 单店；预测留到第四阶段 |
| 原料批次与效期明细 | 阶段一暂不进入 | 按原料汇总库存，不声称已有批次追溯 |
| 真实顾客资料 | 不提交仓库 | 样例全部虚构 |
