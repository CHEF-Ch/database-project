# 第一周：经营场景与业务需求

> 本周不写 SQL、不建表，重点是**定边界、定角色、定流程、定规则**。产出：业务流程、角色与职能清单、数据边界清单、业务规则清单。

## 1. 项目定位与边界

- **项目名称**：奶茶店经营管理系统（暂定名，可改）
- **一句话定位**：服务一家校园周边奶茶店，销售现制饮品，覆盖**到店点单**与**外卖平台订单**，并提供会员积分/优惠券/储值、原料级库存与加料定制。
- **场景**：奶茶店（单门店、单币种人民币）

**复杂度控制（明确"不做"什么，防止越做越大）**：

| 项 | 本版决定 |
| --- | --- |
| 销售渠道 | 到店（COUNTER：收银台代录 + 扫码小程序自助点单）+ 外卖平台（PLATFORM：美团/饿了么）；**不做自营商城**（小程序为到店自助点单、现场取餐，非送货商城） |
| 外卖范围 | 只做**平台侧**：记录平台订单号、平台抽成、配送地址与配送费；门店到"交餐给平台骑手"为止，**不管理骑手、不跟踪配送轨迹** |
| 定制粒度 | **重定制**：糖度 / 冰量 / 温度 + **加料**（珍珠/椰果/布丁等）；加料会按其用量**扣减对应原料库存** |
| 库存口径 | **原料级**：按"配方 + 加料"扣料，而非卖一杯扣一杯成品 |
| 会员 | 积分、优惠券、储值（余额）；积分/余额保留流水 |
| 退款 | 阶段一仅支持**整单退款**，不支持部分退款 |

## 3. 业务流程

### 主流程一：到店点单

1. 顾客到店，两种下单方式：**扫码小程序自助**（顾客手机点单，登录即会员或游客）或**收银台代录**（收银员选饮品、杯型、糖度/冰量/温度、加料、数量）
2. 关联会员：小程序登录即会员；收银台可扫小程序码（可选）→ 校验可用券/余额 → 计算商品金额（商品价 + 加料费 − 券优惠）
3. **预占原料**：核对可售量（现存量 − 预留量）→ `预留量 += 用量`，**不动现存量、不写流水**；锁定券；订单 = `PENDING`。同一原料不可被多笔未完成订单重复预占
4. 顾客付款（现金 / 线上支付 / 会员余额）。现金单交易窗口极短，收款确认后直接进入第 5 步
5. **确认耗用**：支付（收款）成功 → `预留量 −= 用量`、`现存量 −= 用量`、**写库存流水**；核销券、扣余额、按实付累计积分（余额支付不计，见 4.1）→ 订单 = `PAID`，进入制作队列
6. 制作员按定制制作 → 出餐 → 顾客取餐

> **预占 / 确认 / 释放三动作**：预占只减可售量、不动现存量、不写流水；确认才减现存量并写流水；释放（取消或超时）仅 `预留量 −= 用量`，不动现存量、不写流水。三者均须**幂等**——以订单号 + 支付流水号做唯一标识，重复通知不重复执行。

### 主流程二：外卖平台订单

1. 顾客在外卖平台（美团/饿了么）下单 → 平台向门店下发订单（平台订单号）
2. 门店收单 → 录为 PLATFORM 渠道订单，记配送地址与配送费
3. 校验可售量 → **接单即确认耗用**（平台单已由平台预收款、无待支付保护期，故不设预占）→ 写库存流水 → 订单 = `PAID`
4. 制作员制作 → 打包交餐给平台骑手（门店职责到此为止）
5. 后续配送由平台负责，门店不跟踪；结算时按平台抽成对账

### 主流程三：补货入库

1. 库存管理员巡检，或系统提示现存量低于安全库存 → 提出补货需求（哪些原料、补多少）
2. 向供应商下单采购（供应商仅记名称，不建独立供应商系统）
3. 原料到货 → 验收入库 → 记正向库存流水 → 原料现存量增加
4. 补货单标记完成

### 配套流程

#### 会员入会（建档）

- 小程序首次登录（微信授权 / 手机号绑定）自动建档；收银台场景引导非会员扫小程序码注册入会。

#### 会员充值

1. 会员选择充值金额 → 发起充值（待支付）
2. 外部支付（微信/支付宝）确认成功 → 增加余额 + 写储值流水（正向，带外部参考号）+ 按充值金额计积分（见 4.1）
3. 同一外部支付流水只入账一次（幂等）；失败 / 超时不加余额
4. 充值**不是销售**：不计销售额；余额消费时不再计分（见 4.1）

#### 发券 / 领券

1. 店长创建券活动（满减规则 + 有效期 + 发放范围）
2. 向会员发券（或会员领取）→ 记录会员—券归属（状态 = 未使用）
3. 之后进入 4.4 的使用 / 核销 / 退回流转

### 异常流程

| 场景 | 处理流程与数据影响 |
| --- | --- |
| 原料不足 | 提示更换商品/加料，或拒绝下单；不产生超卖 |
| 未付款取消 / 超时 | 释放原料预占与券锁定，不产生退款与积分；释放动作须幂等，重复通知不重复释放 |
| 已付款取消 | 整单退款，退回余额/积分冲正；已耗用原料不自动恢复 |
| 会员余额不足 | 整单改用其他渠道，或先充值 |
| 券不符合条件 | 校验归属/有效期/门槛，不满足则不可用 |
| 加料缺货 | 该加料不可选，提示顾客 |
| 盘点 / 损耗 | 损耗记负向流水，盘盈盘亏差异记录原因，不覆盖历史 |
| 制作失败 / 重做 | 额外原料损耗另行登记，不修改标准销售耗用记录 |
| 平台订单取消/异常 | 按平台通知处理，保留平台订单号便于对账 |
| 平台单重复下发（幂等） | 同一平台订单号推两次时只录一笔，不重复扣料；平台订单号唯一防重 |
| 对账差异 | 平台结算抽成/金额与门店记录不符，按平台订单号核对并登记差异 |
| 支付回调超时 | 顾客已付款但门店未收到成功通知，人工核对后补录，避免漏单 |

## 4. 业务规则

> 这些规则直接决定第 2 周表结构和第 3 周 SQL，逐条经组内确认。

### 4.1 积分规则

- **每满 1 元记 1 分**，按订单**实付**计（已扣券优惠、已含加料费），不含配送费。**仅对会员的到店单累计**；平台单不积分：平台已抽成 20%，门店实收偏低，积分成本由门店承担，故平台单不参与积分体系。非会员游客单同样不计分。
- **储值也计分，但只计一次**：充值时按充值金额计分；用余额消费时不再计分（该笔钱充值时已计过），避免重复计分。
- **取整**：不满 1 元的部分不计（实付 15.6 元 → 记 15 分），不产生小数分。
- **支付成功才记**；未付款、已取消、已退款的不记，退款时冲正已记积分并保留冲正流水。
- 第一阶段积分**只累积、不消耗**（积分兑换留待后续阶段）。

### 4.2 加料费

- **默认小料 ≠ 加料**：商品配方里**已含**的小料（如珍珠奶茶自带的珍珠）算在商品价内、扣料也在配方用量内，**不算加料、不额外收费**；"加料"特指在默认配方之外**额外添加**的小料。同一原料可既是某商品的默认配方料、又是其它商品的加料选项（珍珠 = 珍珠奶茶的默认料，也可作为四季春茶的加料）。
- **加料既扣料、也加钱**：每种加料有**独立单价**（如珍珠 +2 元、椰果 +1 元）。
- **金额影响**：**商品金额** = 商品价 + Σ(加料单价 × 数量) − 券优惠。门店订单的金额只到"商品金额"为止；配送费属平台侧，不进门店订单金额（见 4.3）。
- **库存影响**：加料按配方用量**扣对应原料**，与饮品主料同规则。
- **同款加料多份**：允许"珍珠 ×2"，费用与扣料均按数量累加。
- **缺货**：加料缺货时该加料不可选（见异常流程表）。

### 4.3 平台抽成

- **固定比例 20%**（样例值，可改），不做分档，作为字段存在。
- **款项流转**：平台单由平台收款，顾客支付的商品款与配送费**均不进门店账目**，门店侧只有一笔流入 = 平台结算款。因此配送费**不是代收转付**，门店完全不参与，仅在平台订单信息里作为**记录字段**留痕（用于对账与解释顾客实付构成）。
- **记录口径**：平台订单信息里记平台名、平台订单号、**抽成比例**、**抽成额**、配送费。
- **抽成基数 = 商品金额**（商品价 + 加料费 − 券优惠），不含配送费。
- **抽成额** = 商品金额 × 20%。
- **门店实收** = 商品金额 − 抽成额（即平台结算款，对账、算真实营业额用）。平台单不参与积分体系（理由见 4.1）。
- **金额口径分层**：顾客实付 = 商品金额 + 配送费（配送费归平台）；门店只关心商品金额与结算款。

### 4.4 券规则

- **只做满减券**（满 X 元减 Y 元），不做折扣券、无门槛券、运费券。
- **只做**到店会员的**商家券**；平台单的券（平台发放，或商家在平台侧发放）涉及**成本分摊**——需在抽成之外单独记录商家承担金额并与平台对账——本版不做，留待后续阶段（见第 6 节）。
- **门槛口径**：满减门槛按**券前金额**（商品 + 加料）算。
- **每单最多用一张券**，不可叠加。
- **校验点**：归属（谁的券）、有效期、是否已用、是否满足门槛。
- **状态流转**：未使用 → 已锁定（下单）→ 已核销（支付成功）/ 已退回（取消或整单退款）。
- **退款**：整单退款时券**退回**为未使用，而非作废。
- **优惠快照**：订单明细记录券前金额与券优惠快照，券规则后续变更不影响历史订单。

### 4.5 订单来源与订单号

- **渠道**（订单主表字段，枚举）：`COUNTER` 到店 / `PLATFORM` 平台，决定订单走哪套流程。
- **下单方式**（仅到店单，字段）：`收银台代录` / `扫码小程序自助`，决定谁录入、如何关联会员；平台单无此维度。
- **平台名**（平台订单信息子表字段）：仅当渠道 = PLATFORM 时存在，如 `美团` / `饿了么`；到店单**无此行**。
- **门店订单号**（订单主表主键）：门店**自己生成、所有来源统一连续编号**，到店单与平台单共用一个编号。
- **平台订单号**（平台订单信息子表字段）：外部平台（美团/饿了么）给的**外部单号**，仅平台单有，用于对账与防重，**唯一（幂等键）、但不是主键**。
- **差异字段归属**：平台订单号、抽成比例/额、配送地址、配送费只在渠道 = PLATFORM 时存在，挂平台订单信息子表；到店单不关联。

### 4.6 订单状态机

> 到店单与平台单**共用同一套状态机**，三处差异："完成"的定义（到店 = 顾客取餐，平台 = 交餐给骑手）、平台单无待支付阶段、平台单不设预占（见下）。

```
PENDING(待支付) → PAID(已支付) → MAKING(制作中) → COMPLETED(已完成)
     ↓               ↓                ↓
 CANCELLED(已取消)   └────────────────┴──→ REFUNDED(已退款)
```

| 状态 | 含义 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| PENDING 待支付 | 已下单未付款 | 下单成功（预占原料/锁定券） | 付款成功 / 取消或超时 |
| PAID 已支付 | 已付款待制作 | 支付（收款）成功（确认耗用/核销券/扣余额或计积分） | 进入制作队列 / 整单退款 |
| MAKING 制作中 | 制作员接手制作 | 制作员接单 | 出餐完成 / 整单退款 |
| COMPLETED 已完成 | 已出餐/交付 | 出餐完成 | 终态 / 整单退款 |
| CANCELLED 已取消 | 未付款取消 | **仅由 PENDING** 取消/超时进入 | 终态（释放预占，不计积分） |
| REFUNDED 已退款 | 已付款后退款 | PAID / MAKING / COMPLETED 整单退款 | 终态（退余额/退回券/冲正积分） |

- **`PENDING` 的适用范围**：仅用于**存在待支付窗口**的下单方式（小程序自助、线上支付）。**收银台现金单**因下单与收款连续发生（交易窗口极短），收款确认即进入 `PAID`，不实际停留在 `PENDING`；预占与确认仍在同一次操作内完成，字段变化同第 3 节主流程一的说明。
- 平台单由平台**预收款**，门店收到即 `PAID` 起步，**无 `PENDING` 阶段**（接单即确认耗用，不设预占）；`PENDING → CANCELLED`（未付款取消）仅对到店单。
- **退款来源**：`PAID` / `MAKING` / `COMPLETED` 均可发起整单退款；`MAKING` 之后退款**已耗用原料不追回**（损失留在原料侧，不修改销售耗用记录）。
- `CANCELLED` 的来源**仅有 `PENDING`**（即未付款取消）；已付款单一律走 `REFUNDED`，两者不可混用。
- `CANCELLED` / `REFUNDED` 为**终态**，不可再跳转。
- 状态机本周只做**业务定义**；用 `CHECK` 约束或状态字段落地留到第 3、4 周。

### 4.7 保质期与临期预警

> 本版记"**这类原料能放多久**"，不记"**这批货哪天到期**"；后者属批次级模型，见第 6 节。

- **保质期是原料的固有属性**：每种原料可设一个**保质期天数**（如珍珠 30 天、鲜奶 7 天），记在原料表。**允许为空**，为空表示该原料**不管控效期**（如糖浆、杯具）；逐原料决定是否管控。
- **到期时间为推算值**：系统**不记录**真实到期日；临期判断按 **入库时间 + 保质期天数** 推算。
- **推算基准**：取库存流水中的**正向入库记录时间**，加保质期天数得推算到期日。
- **推算的局限（重要）**：同一原料多次入库会产生**多条**临期记录，每条只表示"**那次入库的货**"，**不代表当前还剩多少**。系统**不追踪**同原料不同入库批次之间的消耗顺序，故临期提示为**提醒性质**，不构成"某批还剩 X"的定量结论；定量需批次级模型（见第 6 节）。
- **预警阈值为查询参数**：不硬编码（如"剩余 ≤ 7 天"），提供"全部有保质期的原料 + 推算到期日 + 剩余天数"，由查询侧筛选。
- **临期不改变任何流程规则**：不阻止下单、扣料、制作，**只提示不拦截**；不产生额外库存流水。处置方式（优先使用 / 促销 / 报损）由人工决定，若报损则走**损耗**流程记负向流水。

## 5. 数据边界：进库

> 判断标准：是否被多个流程共享？未来要不要查询/统计/留痕/预测？是否随时间变化需留历史？

| 数据 | 主要内容 | 原因 |
| --- | --- | --- |
| 商品 | 名称、杯型、售价、上下架状态 | 统一定价与点单 |
| 原料 | 名称、单位、现存量、预留量、安全库存、保质期天数 | 原料级库存，支撑缺料判断与补货触发；保质期天数用于临期预警（见 4.7） |
| 配方 | 商品—原料、每杯标准用量 | 一杯饮品耗用哪些原料 |
| 加料 | 珍珠/椰果等，及其单价、单位用量 | 定制扣料，加料本身也是原料 |
| 订单 | 渠道、下单方式、会员、金额组成（商品金额、券优惠额；平台单另记配送费）、状态、时间 | 追踪完整交易；金额分层见 4.3 |
| 订单明细 | 商品/规格快照、**杯数**、成交价、糖度/冰量/温度 | 一行 = 一款饮品及其杯数（**同款同定制合并**）；历史订单不随商品调价变化 |
| 订单加料明细 | 每行明细的加料及用量 | 定制扣料与追溯 |
| 会员 | 编号、联系方式、积分、余额 | 关联订单与会员权益 |
| 积分/储值流水 | 变动类型、金额、关联订单/充值来源 | 解释"为什么是这个数" |
| 优惠券 | 规则、有效期、会员领券与使用状态 | 防重复使用/用他人券 |
| 员工 | 编号、姓名、职务、在职状态 | 经办与权限依据 |
| 补货单 | 原料、数量、供应商名称、状态、时间、经办 | 补货入库的来源与追溯 |
| 库存流水 | 出入库类型、数量、经办、关联订单/补货单 | 库存可追溯 |
| 平台订单信息 | 平台名、平台订单号、抽成比例/额、配送地址/费 | 平台对账与结算 |

## 6. 数据边界：不进库 / 暂不进入

| 数据 | 决定 | 原因 |
| --- | --- | --- |
| 骑手信息、配送轨迹、地图路线 | 不进入 | 配送归平台，门店不管理 |
| 第三方平台内部数据 | 暂不进入 | 只存平台订单号/抽成用于对账 |
| 支付密码、银行卡、平台密钥 | 不作为业务数据存储 | 由支付服务处理，密钥不进 Git |
| 身份证、生日、健康资料 | 不收集 | 完成购买不需要 |
| 浏览轨迹、广告画像、聊天录音 | 不进入 | 本版聚焦交易 |
| 供应商合同、工资、水电、税务 | 暂不进入 | 不建完整财务/人事系统 |
| 多门店调拨、自动采购预测 | 暂不进入 | 单店；预测留到第四阶段 |
| 平台券及成本分摊 | 阶段一暂不进入 | 需在抽成之外单独记录商家承担额并与平台对账 |
| 原料批次级明细（批次号、逐批到期日、逐批成本） | 阶段一暂不进入 | 保质期本身已进库（原料表保质期天数 + 临期视图，见 4.7）；批次级追溯需重建库存模型（FIFO、跨批扣料），留阶段二评估 |
| 真实顾客资料 | 不提交仓库 | 样例全部虚构 |

## 7. 本周小组确认事项

- 已确定：奶茶店场景、会员体系、原料库存（含补货入库）、重定制（含加料）、外卖平台渠道（不建骑手）。
- 业务规则已确定：积分（每满 1 元记 1 分）、加料费（加料收费有单价、默认小料不另计）、平台抽成（固定 20%、按商品金额计）、券（满减、每单一张、退款退回）、订单来源（COUNTER/PLATFORM + 下单方式 + 平台名 + 双层单号）、状态机（6 状态；平台单无 `PENDING`、不设预占）、库存三动作（预占 / 确认 / 释放）、保质期与临期预警（原料保质期天数 + 推算）——详见第 4 节。
- 需重点能解释的概念：**原料 vs 商品**、**默认小料 vs 加料**、**加料为何也扣料**、**补货流程 vs 补货预测**、**充值收入 vs 销售额**、**平台抽成 vs 门店实收**、**商品金额 vs 顾客实付**、**预占 vs 扣减**。

**本版简化说明（有意为之，非遗漏）**：

- 平台抽成固定 20%，现实为分品类 / 分配送方式费率，并含保底抽成与活动补贴分摊；
- 积分在"消费或储值"中只计一次，现实常用"充值送券 / 送余额"而非送积分；
- 券只做满减且每单一张、不可叠加，现实券种更多，且平台券需做成本分摊；
- 退款仅支持整单，现实常按制作进度协商或部分退款；
- 加料缺货由系统自动禁用，现实多为店长手动下架；
- 储值仅记余额与流水，不做充值档位、赠送规则与有效期。

以上简化均为控制阶段一复杂度，不影响核心链路可运行。
