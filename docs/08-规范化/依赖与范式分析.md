# 第六周 ②：函数依赖与更新异常分析

> 对象：v0.1 的 17 张表（`MilkTeaShop`，结构指纹 219 项，基线见 [`result/第6周-①迁移前基准-说明.md`](../../result/第6周-①迁移前基准-说明.md)）。
> 事实来源：业务规则 [`docs/01` §4](../01-业务流程与数据边界.md)、关系模式与候选码 [`docs/02` §2/§3/§5.2](../02-数据字典.md)、联系与实现方式 [`docs/07-ER模型/业务规则与映射清单.md`](../07-ER模型/业务规则与映射清单.md)、实际约束 [`sql/constraint.sql`](../../sql/constraint.sql)。
> 口径：**函数依赖来自业务规则，不由样例取值推断**；候选码以 `docs/02` §5.2 为准；异常例子一律用 `02-seed.sql` 的真实行（订单号、原料号可直接对照）。

## 0. 结论速览

| 项 | 结果 |
| --- | --- |
| 1NF | 17/17 通过（属性原子、无重复组；"每单最多一张券"使 `coupon_discount` 保持单值） |
| 2NF | 17/17 通过（6 处复合候选码逐表查过，无部分依赖） |
| 3NF / BCNF | **16/17 通过；`shop_order` 有 1 处严格违例**：`{item_subtotal, coupon_discount} → total_amount` |
| FD 冗余导致的经典异常 | 1 处（`shop_order.total_amount` 的修改/插入异常） |
| 跨表派生/快照 | 10 类已存列（会员积分/余额、库存两量、订单行价格/杯型、抽成额、供应商名、券优惠、订单总额），**不是表内 FD 违例**，但有一致性风险 |
| 结构缺口 | **1 处**：`order_item_addon` 缺 `addon_price` 快照（S1），历史加料金额会随现价漂移；不是 3NF 违例，补列解决 |
| 约束缺口 | v0.1 问题清单 P1–P11；本次分析新增 **P12**（`total_amount` 等式）；P10 已在 `docs/02` 回填 |

> 一句话：**v0.1 基本已在 3NF/BCNF，唯一真正的规范化问题是订单总额这个派生列；其余"冗余"都是有意的快照或跨表聚合，要靠事务/约束维护，不能靠拆表解决。**

## 3. 唯一的严格 3NF 违例：`shop_order.total_amount`

### 3.1 依赖链

```text
order_id → item_subtotal, coupon_discount      （order_id 是主码，当然成立）
{item_subtotal, coupon_discount} → total_amount （业务定义：total = subtotal − discount）
⇒ order_id → total_amount 经非主属性传递
```

- 决定因素 `{item_subtotal, coupon_discount}` **不是超码**：多张订单可以有相同的券前金额与券优惠（例：多张订单都可能是 34.00 − 0.00）。
- 被决定属性 `total_amount` **不是主属性**（候选码是 `order_id` / `pay_txn_no`）。
- 因此不满足 3NF，也不满足 BCNF；这是全库唯一一处。

### 3.2 具体异常

**修改异常（最典型）**

```sql
-- 迁移前：单 1 是 34.00 − 0.00 = 34.00
UPDATE dbo.shop_order SET item_subtotal = 30.00 WHERE order_id = '202609160001';
-- 结果：item_subtotal = 30.00，coupon_discount = 0.00，total_amount 仍 = 34.00
-- 顾客被多收 4 元；现有 CK_shop_order_total_amount 只查 >= 0，拦不住
```

**插入异常**

```sql
-- 只要 total_amount >= 0，就能写进一张自相矛盾的订单
INSERT INTO dbo.shop_order
    (order_id, channel, order_mode, order_status, member_id, employee_id,
     item_subtotal, coupon_discount, total_amount, pay_method, created_at)
VALUES
    ('202609169998', 'COUNTER', 'COUNTER_CASHIER', 'PAID', NULL, 'E0000001',
     10.00, 0.00, 999.00, 'CASH', '2026-09-16 17:00:00');
```

**删除异常**

- 标准意义上的删除异常（删一行丢失另一实体的信息）**不存在**：`total_amount` 没有独立实体，删订单就该删总额。
- 但删 `PENDING` 单 5 会留下未释放的预占：明细/加料随订单级联删除，`reserved_qty` 仍是 30/150/5/25/20/1。这不是 `total_amount` 造成的，而是"预占释放"没有结构约束，单独记一笔（不改变 3NF 结论）。

### 3.3 为什么不能简单说"拆表"

`total_amount` 不是"另一个实体的属性"，而是同一行内的算术派生。把它拆到一张新表只会得到 1:1 的 `order_amount(order_id, ...)`，既没有消除依赖，又增加连接；真正的规范化做法是**删掉派生列、查询时计算**。但本项目有两条硬约束：

1. `CHECK (total_amount >= 0)` 需要一个可约束的列（删掉就没法用 CHECK 表达"券优惠不得超过券前金额"）；
2. `02-seed.sql`、`crud.sql`、四个视图与第 4 周证据都按 `total_amount` 列名写入/查询，改成计算列会破坏 v0.1 的可复现性（课程要求"迁移在副本上做、v0.1 源库不动"，不是"改掉 v0.1"）。

因此 ③ 的候选方案是：**保留 `total_amount`，用 `CHECK (total_amount = item_subtotal - coupon_discount)` 把"派生关系"变成"不可分叉的约束"**（P12），而不是拆表。这样严格 3NF 的定义仍不满足，但更新/插入异常被结构性地消除——这是"保留 + 约束"的工程口径，需在 ③ 里用无损连接/依赖保持论证并记录取舍。

## 4. 跨表派生与快照：不是表内 FD 违例，但有一致性风险

> 这些列由**另一个表/另一组行**决定，不属于单表 3NF 的判定范围；拆表也解决不了（拆出去仍是 1:1 或聚合），只能靠事务、约束或对账查询维护。

| 派生/快照 | 来源 | 表内 FD 违例？ | 维护方式 | 不一致的后果 |
| --- | --- | --- | --- | --- |
| `shop_order.total_amount` | 同行 `item_subtotal − coupon_discount` | **是**（§3） | P12 等式 CHECK | 多收/少收，退款金额错 |
| `order_item_addon.addon_price`（**缺**） | `item_addon_option.addon_price` 的下单时点值 | 否（跨表、跨时间） | S1：加列 + 下单时写入 + 回填 | 调价后历史加料金额被重算，行金额+加料金额 ≠ 小计 |
| `order_item.size` | `item_product.size` 的下单快照 | 否（`product_id ↛ size`，改杯型不影响历史） | 下单时写入，之后不改 | 若改历史行，历史杯型失真 |
| `order_item.unit_price` | `item_product.unit_price` 的下单快照 | 否（`product_id ↛ unit_price`，价格随时间变） | 下单时写入，之后不改 | 改历史行会篡改成交价 |
| `member_member.points` | `member_point_log` 净额 | 否（键决定，非表内传递） | 同事务写快照 + 流水；`CHECK >= 0` | 积分与流水对不上（例：118→200） |
| `member_member.balance` | `member_balance_log` 净额 | 否 | 同事务；`CHECK >= 0` | 余额与流水对不上 |
| `item_material.stock_qty` | 期初 + `inv_stock_log` 净变动 | 否 | 同事务；`CHECK >= 0`；期初未入流水（已知限制） | 库存与流水对不上，无法从流水完全复原 |
| `item_material.reserved_qty` | 待支付订单的配方+加料需求 | 否 | 预占/确认/释放同事务；`CHECK <= stock_qty` | 删待支付单不释放 → 预占泄漏 |
| `order_platform.commission_amount` | `shop_order.total_amount × commission_rate` | 否（跨表） | 下单时计算写入；对账查询 | 改费率不重算 → 抽成错 |
| `inv_restock.supplier_name` | 采购时点的供应商名 | 否 | 视为快照，不回头改名 | 若按实体改名，历史单分裂 |
| `shop_order.coupon_discount` | 券规则 + 核销时点 | 否 | 下单时写入；规则变更不影响历史 | 改历史行会篡改优惠 |

> 这 10 类已存列里，只有 `total_amount` 同时是"表内 FD 违例"；其余是"快照/聚合"，**不该用拆表解决**。`order_item_addon.addon_price` 则是"该有而没有"的快照列（S1），处理方式是**补列**，不是拆表或加 CHECK。这条区分是 ③ 判"保留/补列"还是"拆分"的核心依据。

## 5. 汇总

| 维度 | 结论 |
| --- | --- |
| 1NF | 17/17 通过。`order_item_addon` 已把"一杯多种加料"拆成多行；`shop_order` 的单张券优惠是单值（业务规定每单最多一张券，若允许多张则需拆表，届时会违反 1NF） |
| 2NF | 17/17 通过。复合候选码 6 处：`item_product(name,size)`、`item_recipe`、`item_addon_option`、`order_item`、`order_item_addon`、`inv_restock_item`；逐项查过无部分依赖 |
| 3NF / BCNF | 16/17 通过；`shop_order` 因 `total_amount` 违例 |
| 经典异常 | 1 处（`shop_order.total_amount`）；其余表的"异常"是约束缺口（P1–P12）或跨表一致性，不是 FD 冗余 |
| 结构缺口 | 1 处（S1：`order_item_addon` 缺 `addon_price` 快照）；补列 + 回填，不改变 3NF 结论 |
| 需要拆/并的表 | **0 张**。没有发现"拆了能消除 FD 冗余"的关系；`order_platform`/流水表/关联表已经是正确分解的结果 |
| 需要新增的约束 | P1–P8、P12；P9 留 v2.0；P10 已回填；P11 先回填 `docs/02` 再落 P8 |
| 需要新增的列 | S1：`order_item_addon.addon_price DECIMAL(10,2) NOT NULL`（快照；回填 3 行） |
| 需要补的文档 | P11：`unit_price > 0`、`commission_amount >= 0`、`item_subtotal >= 0`、`coupon_discount >= 0`、`refund_amount >= 0` 等值约束未写入 `docs/02` §2.2（值约束） |
