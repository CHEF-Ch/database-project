## 1. 判定口径与取舍规则

### 1.1 范式口径

- **1NF**：每个属性原子、无重复组、无多值属性。
- **2NF**：在 1NF 基础上，**每个非主属性都不部分依赖任一候选码**（复合候选码要逐列检查）。
- **3NF**：对每个非平凡 FD `X → A`，或 `X` 是超码，或 `A` 是主属性；等价地，非主属性不能传递依赖于候选码。
- **BCNF**：每个非平凡 FD 的决定因素都是超码。

### 1.2 保留 / 拆分 / 合并的取舍规则

| 规则 | 说明 |
| --- | --- |
| R1：FD 冗余才考虑拆 | 只有"非主属性传递依赖非超码"或"部分依赖"才拆；样例重复值不算证据 |
| R2：快照不拆 | 价格/杯型/积分/余额/库存等"写入时点快照"与源表是**时间维度**的差异，拆掉就丢历史；保留并在文档里说明维护方式 |
| R3：1:1 不拆 | 拆成 1:1 只增加连接，不消除任何 FD；除非有独立生命周期/权限边界 |
| R4：无损连接 + 依赖保持 | 任何拆分都要能通过自然连接还原，且原 FD 仍可推导；做不到就不拆 |
| R5：v0.1 可复现 | 迁移只加不改；不重写 `01-schema.sql`/`02-seed.sql` 的既有列，避免"迁移前的库"无法复现 |
| R6：约束优先于拆表 | 能用 CHECK/唯一索引消除的异常，优先加约束，而不是拆表 |

> 按 R2/R3/R5，`item_product`、`order_item`、`member_member`、`item_material`、`inv_restock` 的"冗余"都不拆；按 R1，`shop_order.total_amount` 是唯一需要处理的 FD 违例；按 R6，用 P12 而不是拆表。

## 3. 问题关系的处理方案

### 3.1 `shop_order.total_amount`：保留 + 等式 CHECK（不拆）

#### 方案比较

| 方案 | 做法 | 无损连接 | 依赖保持 | 对 v0.1 的影响 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **A（采用）** | 保留 `total_amount`，加 `CHECK (total_amount = item_subtotal - coupon_discount)` | 不分解，恒等无损 | FD 被 CHECK 强制，存储层保持 | 只加约束；`01-schema`/`seed`/`crud`/视图不用改 | ✅ |
| B | 删掉 `total_amount`，查询/视图里计算 | 可计算还原，信息不丢 | FD 退化为应用逻辑，数据库不再保证 | 改 `02-seed.sql`、`crud.sql`、4 个视图、第 4 周证据；`CHECK(total>=0)` 失去落点 | ❌ |
| C | 改成 `AS (item_subtotal - coupon_discount) PERSISTED` 计算列 | 无损 | FD 由计算列保证 | `02-seed.sql`/`crud.sql` 显式插 `total_amount` 会报"不能插入计算列"；需要改脚本 | ❌（留 v2.0 评估） |

#### 为什么 A 可接受

- **严格 3NF 仍不满足**：`{item_subtotal, coupon_discount}` 不是超码，`total_amount` 不是主属性。这一点不掩饰。
- 但 ② §3 的两类异常（改小计不改总额、插入自相矛盾的总额）**被 P12 结构性消除**：任何写入都必须满足等式，冗余列不可能与来源分叉。
- 这属于"**受约束的派生属性**"工程处理：不追求教科书式的"删列"，而是让派生关系不可违反。对课设而言，保留 `total_amount` 还能让 `CHECK(total_amount >= 0)`、退款金额、平台抽成基数继续有落点。
- **无损连接**：没有分解，恒等分解显然无损。
- **依赖保持**：`{item_subtotal, coupon_discount} → total_amount` 由 P12 在存储层强制，依赖没有丢；其余 FD 不受影响。

#### 冗余维护

- 写入侧：下单/改单时一条语句同时写 `item_subtotal`、`coupon_discount`、`total_amount`；P12 兜底。
- 对账侧：⑤ regression 用 ① §5.4 的查询核对 `total_diff = 0`。
- 不在应用层"只改小计"——即使改了，P12 会拒绝，错误在写入点暴露。

### 3.2 S1：`order_item_addon` 缺 `addon_price` 快照（新增 1 列）

#### 问题

`order_item_addon` 只存 `(order_id, item_line, material_id, qty)`。加料金额一直用**当前** `item_addon_option.addon_price` 重算：

```sql
-- query.sql 13 的算法
SUM(oia.qty * a.addon_price)   -- a = item_addon_option（当前价）
```

- `order_item.unit_price` 是下单时快照，商品调价不影响历史；
- 但加料单价没有快照，`item_addon_option.addon_price` 一改，**历史订单的加料金额就被重算**：
  - 种子单 1：四季春 + 珍珠 ×1，当前 2.00；若店长把珍珠加料调到 3.00，单 1 的加料金额从 2.00 变 3.00，而 `item_subtotal` 仍是 34.00 → 行金额 + 加料金额 ≠ 小计。
  - `query.sql` 13 的 `subtotal_diff` 会从 0 变成 **+1.00**；历史报表失真。
- 这是**快照缺失**，不是 3NF 违例（加料单价依赖"这一行"而不是商品或原料单边）；拆表解决不了，必须补列。

#### 方案比较

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| **A（采用）** | `order_item_addon` 增加 `addon_price DECIMAL(10,2) NOT NULL`，下单时写入当时的加料单价；回填现有 3 行 | ✅ 与 `order_item.unit_price` 对称，历史金额稳定 |
| B | 不改结构，约定"加料价永不变" | ❌ 与"店长可维护加料价"的业务矛盾；调价即失真 |
| C | 另建"加料销售"表 | ❌ 1:N 明细已经承载关系属性，另建表只是把同一行拆成 1:1，增加连接不消除问题 |

#### 迁移步骤（④ 实施）

```sql
-- 1) 先加可空列
ALTER TABLE dbo.order_item_addon ADD addon_price DECIMAL(10,2) NULL;
GO
-- 2) 用当前价回填（仅当样例价格未变；见下方限制）
UPDATE oia
SET addon_price = a.addon_price
FROM dbo.order_item_addon AS oia
JOIN dbo.order_item AS oi
  ON oi.order_id = oia.order_id AND oi.item_line = oia.item_line
JOIN dbo.item_addon_option AS a
  ON a.product_id = oi.product_id AND a.material_id = oia.material_id;
GO
-- 3) 确认无 NULL 后收紧为 NOT NULL
ALTER TABLE dbo.order_item_addon ALTER COLUMN addon_price DECIMAL(10,2) NOT NULL;
GO
-- 4) 值约束（计入 P8）
ALTER TABLE dbo.order_item_addon
  ADD CONSTRAINT CK_order_item_addon_addon_price CHECK (addon_price > 0);
GO
```

**回填限制（必须写进迁移说明）**：用当前价回填只对"**样例库自 seed 以来加料价未改过**"成立。本项目 v0.1 样例价格未变，3 行回填值与历史一致；若在真实环境执行，必须用历史价（如订单快照/对账表）回填，不能直接取当前价。

**无匹配风险**：`order_item_addon` 只外码到 `item_material`，不保证 `(商品,加料)` 仍在 `item_addon_option` 里。迁移前须检查"回填后仍为 NULL"的行数；本项目为 0，若 >0 应中止并人工处理。

#### 无损连接与依赖保持

- 加列是**关系扩展**：把新关系投影回原 4 列，得到原关系，信息不丢 → 无损。
- 新 FD `(order_id, item_line, material_id) → addon_price` 写入即成立；原 FD 全部保留。
- 该列是**快照**，不引入对 `item_addon_option` 的跨表传递依赖；3NF/BCNF 仍成立。

#### 连带更新

- `docs/02` §2.2-7 增加 `addon_price` 字段（非空，`> 0`）；
- `docs/02` §3.2 的 `order_item_addon` 行补"加料单价快照"；`docs/07-ER模型/业务规则与映射清单.md` §2 R7 同步；
- `docs/07-ER模型` 的 ER 图/映射清单在 ⑥ 同步（`order_item_addon` 增加属性）；
- `query.sql` 13 在 v1.0 应用侧改用 `oia.addon_price`（v0.1 的 `query.sql` 作为历史证据不改）。

### 3.3 供应商主数据：考虑后不拆

若把 `inv_restock.supplier_name` 拆成 `supplier(supplier_id, name)` + `inv_restock.supplier_id`：

- **无损连接**：按 `supplier_id` 自然连接可还原，`supplier_id` 是 `supplier` 的码、`inv_restock` 的外码 → 无损。
- **依赖保持**：`supplier_id → name` 保留在 `supplier`，`inv_restock` 的其余 FD 不变 → 保持。
- **为什么不采用**：
  1. `docs/01` §5 明确"供应商不独立建系统"，只记名称；
  2. `supplier_name` 应理解为**采购时点的名称快照**——供应商后来改名，不应改写历史补货单；拆成主数据反而要决定"历史名还是现名"；
  3. 需要数据迁移、增加一张表与外码，超出本周"结构合理就保留"的范围；
  4. 若将来要管供应商合同/评级，再按 v2.0 迁移。

### 3.4 `order_item.size` / `unit_price`：考虑后保留

- 若删掉两列、改为连接 `item_product` 取当前值：在**某一时点**是无损的（`product_id` 是码），但跨时间不是——商品调价/改杯型后，历史订单会显示新值，丢失成交快照。
- 业务上 `docs/02` §5.6 明确"`order_item.size` 是下单快照，商品改名/改杯型不影响历史明细"；`unit_price` 同理。
- 因此保留；它们不是 FD 冗余（`product_id ↛ size/unit_price` 跨历史不成立），是**时间维度快照**。

### 3.5 `member_member.points/balance`、`item_material.stock_qty/reserved_qty`：考虑后保留

- 删掉快照、改为对流水求和：数学上可还原（无损），但：
  1. `CHECK (balance >= 0)` / `CHECK (reserved_qty <= stock_qty)` 失去落点；
  2. 每次读都要聚合流水，订单/库存查询变慢；
  3. 期初库存没有流水（① §5.3），纯流水无法还原当前库存；
  4. 拆成 1:1 快照表只增加连接，不消除聚合依赖。
- 结论：保留快照，靠事务双写 + 对账查询维护（`docs/02` §5.3 的既有口径）。

### 3.6 其余表

- `item_recipe` / `item_addon_option` / `order_item_addon` / `mkt_member_coupon` 是 4 处 M:N 的关联实体，已是正确分解，不再拆。
- `inv_stock_log` / `member_point_log` / `member_balance_log` 是审计事件表，键决定整行，不再拆。
- `order_platform` 已从 `shop_order` 拆出（1:0..1 弱实体），保持。
- `mkt_coupon_rule` 与 `mkt_member_coupon` 已按"规则/持券"拆开，保持。

## 5. 无损连接与依赖保持

### 5.1 不分解的 17 张表

- 没有做任何关系分解，全部是**恒等分解**：`R = R`，自然连接回自身显然无损。
- 所有原 FD 原样保留；新增的 P12/S1 只增加约束或属性，不删除任何 FD。

### 5.2 `shop_order` 保留 + P12

- 方案 A 不分解：无损连接恒等成立；`{item_subtotal, coupon_discount} → total_amount` 由 CHECK 强制，依赖保持。
- 方案 B（删列）虽然可用计算还原（无损），但 FD 不再由数据库保持，且 `CHECK(total>=0)` 失去落点 → 不采用。
- 方案 C（计算列）由计算列保证 FD，但破坏既有写入脚本 → 留 v2.0。

### 5.3 S1 加列

- 关系扩展 `R' = R ∪ {addon_price}`；投影回原属性 `π_R(R') = R`，无损。
- 新 FD `(order_id,item_line,material_id) → addon_price` 写入即成立；无原 FD 丢失。
- 不是分解，不涉及连接还原；快照语义与 `order_item.unit_price` 一致。

### 5.4 被否决的分解

| 方案 | 无损连接 | 依赖保持 | 否决理由 |
| --- | --- | --- | --- |
| 供应商拆主数据 | ✅（`supplier_id` 连接） | ✅（`supplier_id→name`） | 快照语义、`docs/01` 不建供应商系统、数据迁移成本 |
| 删 `order_item.size/unit_price` 改连接商品 | ⚠️ 仅当前时点无损 | ❌ 跨历史丢失成交快照 | 历史订单会随时间漂移 |
| 删会员/库存快照改聚合 | ✅（SUM 可还原） | ⚠️ 聚合依赖不在表内 | CHECK 失去落点、性能、期初库存无流水 |
| 删 `total_amount` 改计算 | ✅（可计算） | ❌ 数据库不再保证等式 | 破坏 v0.1 脚本与 CHECK |
| 1:1 拆快照表 | ✅ | ✅ | 只增加连接，不消除任何 FD（R3） |

## 8. 结论

1. **17 张表全部保留，0 拆 0 并**：没有发现"拆了能消除 FD 冗余"的关系；现有分解（订单/明细/平台信息、券规则/持券、补货单/明细、流水）已符合 3NF。
2. **唯一 3NF 违例是 `shop_order.total_amount`**：用 P12 等式 CHECK 消除异常，保留派生列；严格 3NF 仍不满足，但这是有约束、有对账、有文档的工程取舍。
3. **S1 补 `order_item_addon.addon_price` 快照**：修复"加料金额随现价漂移"的历史缺陷，与 `order_item.unit_price` 对称。
4. **迁移 = +1 列 + 15 CHECK + 1 索引**，目标指纹 **236**；只回填 3 行，不改业务金额、不改行数。
5. ④ 只在 `MilkTeaShop_v01` 副本执行；v0.1 源库保持 219 项不动。
